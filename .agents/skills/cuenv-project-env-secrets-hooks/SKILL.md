# Project, Env, Secrets, Hooks

Start with `docs/design/specs/schema-coverage-matrix.md`, then read the relevant schema files:

- `schema/core.cue` and `schema/config.cue` for project and command defaults.
- `schema/context.cue` for named contexts (`contexts.<name>` as `schema.#When & {...}` or `schema.#TaskFilter & {...}`), which select `env.context.<name>`; `crates/core/src/context.rs` decides which are active and `crates/manifest/src/context.rs` holds the DTOs.
- `schema/env.cue` and `schema/policy.cue` for env values, policies, interpolation, and passthrough. Environment map keys start with an uppercase ASCII letter or underscore and contain only uppercase ASCII letters, digits, and underscores; shell export also validates names captured from hooks.
- `schema/secrets.cue`, `schema/onepassword.cue`, `schema/infisical.cue`, `schema/aws.cue`, `schema/gcp.cue`, and `schema/vault.cue` for secret shapes.
- `schema/hooks.cue` and `schema/shell.cue` for hooks and shell command variants.
- `crates/core/src/environment/values.rs` for env value shapes, policy checks, interpolation, and secret-aware value resolution; `crates/core/src/environment.rs` for runtime environment merging, PATH lookup, and filtered env construction.
- `crates/core/src/secrets/mod.rs` owns the default secret registry. Keep its fallible `Result` API stable for optional resolver initialization while avoiding local lint suppressions.
- `crates/secrets/src/batch.rs` and `crates/secrets/src/resolved.rs` own runtime batch convenience APIs. Keep caller-facing secret maps generic over the caller's `BuildHasher`; the object-safe `SecretResolver` trait keeps the internal concrete map boundary for provider implementations. Batch env resolver tests should scope fixtures with `temp_env` instead of unsafe process-wide environment mutation.
- `crates/secrets/src/resolvers/exec.rs` owns the private JSON shape for `schema.#ExecSecret`; do not add public constructors for test-only setup.
- `crates/1password/src/secrets/core.rs` owns the WASM SDK host functions. Keep memory offsets checked against the `i64` host ABI boundary and Unix-time conversion saturating rather than cast-suppressed. WASM initialization integration tests should scope `HOME` and `ONEPASSWORD_WASM_PATH` with `temp_env` and return `Result` from fallible setup instead of reintroducing broad `expect_used` or unsafe process-wide mutation allowances.
- `crates/cuenv/src/commands/secrets.rs` owns `cuenv secrets setup` orchestration and provider preflight output. Keep setup messages on redacted output helpers and format download sizes without float casts.
- `crates/hooks/src/state/` owns persistent hook state, execution identities, per-directory reservations, recovery, execution hashes, and integer duration display formatting; persisted state contains sanitized progress and identity metadata rather than hook arguments, output, or captured environment values. `crates/hooks/src/executor.rs` and `crates/hooks/src/executor/hook_executor.rs` own execution orchestration and saturating elapsed-millisecond conversion; `crates/hooks/src/executor/source_environment.rs` owns source-hook environment capture. A cross-process state lock serializes bounded local transactions and exact run identities prevent stale workers or cleanup from affecting a later run. Cancellation keeps the directory reserved until the direct child is stopped and reaped and the worker acknowledges cancellation. Use `cuenv env recover --list` and the exact directory key, instance hash, run UUID, and `--drained` attestation to recover an abandoned run; a missing PID or marker does not establish quiescence. The operator must also drain escaped descendants and old-version supervisors, which do not follow this protocol. Unix hook state uses private owner-controlled directories and 0600 files; only the managed default can tighten an existing owned directory, and its parent must be trusted. Atomic replacement is not a power-loss durability guarantee. Supervisor integration tests must run a real CLI, fail on missing prerequisites or timeouts, and scope `CUENV_EXECUTABLE` with `temp_env` rather than unsafe process-wide mutation.
- Completed hook results live in an authenticated, per-run in-memory broker. The supervisor receives its startup payload through an anonymous pipe with a 16 MiB encoded limit. Each spawned process has a 16 MiB combined stdout/stderr limit, and the accumulated encoded broker result has a separate 16 MiB limit; exceeding a limit fails the run before publication. Different shell sessions and CI runs have distinct UUIDs; A missing broker invalidates that exact generation and permits a guarded rerun, while ambiguous transport or authentication failures fail closed. On Linux the broker uses an abstract socket bound to the exact lease network-namespace identity: automatic lookup and reclaim fail closed if the namespace differs or cannot be verified. After inspecting the exact reservation and draining the relevant processes, use explicit `cuenv env recover --drained` for cross-namespace recovery. No hook payload, output, or captured environment is written to new cuenv-owned state or supervisor logs; operating-system swap and old backups are outside that guarantee. Sessions are identifiers, not authentication. Declared input contents participate in the execution hash, but changes that return to their original value between snapshots are not observable. Ambient changes require a new session or explicit reload.
- Shell integration keeps restoration values in the originating shell, with names-only exported metadata to detect inherited overlays. Each initialized shell keeps its session ID local and passes it only to hook-aware cuenv commands; manual sharing is explicit. Hook starts run against a shell-local pre-overlay baseline so PATH changes do not compound. On project changes it restores the prior environment before evaluating a different project; a nested shell without the private backups must fail closed. `cuenv shell refresh` applies through the guarded parent-shell path and refuses unrelated function, sourced-file and subshell frames. Shell export rejects interpreter-control names and reserved prefixes. Zsh refuses tied variables other than PATH, and refuses PATH arrays that cannot round-trip through the exported scalar. Shell integration requires real interpreter regression tests, including quoting, scope, tracing and child-process boundaries.
- Cucumber BDD coverage keeps the root runner in `crates/cuenv/tests/bdd.rs`; shared world state and env/task/hook step definitions live under `crates/cuenv/tests/bdd_support/`. Keep world initialization, project fixture writes, CUE module setup, env-step tables, task command execution, hook status polling, approval setup, shell execution, and hook failure assertions on fallible `StepResult` paths instead of reintroducing broad unwrap/expect/print allowances or warning-based skipped assertions. The BDD runner fails on undefined or skipped steps; keep that split when adding hook, shell integration, env, or task behavior scenarios instead of growing one oversized BDD file.
- Hook integration tests should share `crates/cuenv/tests/hook_test_support` for temporary CUE module setup and approval; return `Result` from filesystem and command setup; use `Command::new(env!("CARGO_BIN_EXE_cuenv"))`; and fail on approval, execution, or prerequisite errors instead of treating them as passing tests.
- `crates/cuenv/src/commands/hooks.rs` for CLI hook command orchestration; `crates/cuenv/src/commands/hooks/status.rs` for status/starship rendering; `crates/cuenv/src/commands/hooks/shell.rs` for `cuenv shell init` snippets. The shell export path lives in `crates/cuenv/src/commands/export/implementation.rs` and checks approval before starting hooks. Export performance regression tests should keep command execution behind shared `Result` helpers instead of reintroducing file-level unwrap/expect allowances.
- `crates/ci/src/executor/hook_env.rs` for hook-backed environment assembly during CI task execution.
- `crates/ci/src/executor/task_env.rs` for CI task env precedence and passthrough handling.
- Interactive prompt and wait-progress CLI output is rendered in `crates/events/src/renderers/cli/interactive.rs`; keep approval-facing wording aligned there when prompt semantics change.

Generation rules:

- Use `schema.#ExecSecret` for custom command secrets.
- Use `schema.#OnePasswordRef` for 1Password references.
- Use `schema.#InfisicalSecret` for Infisical REST API references. Auth comes from Universal Auth (`INFISICAL_CLIENT_ID` + `INFISICAL_CLIENT_SECRET`), OIDC Auth (`INFISICAL_MACHINE_IDENTITY_ID` + `INFISICAL_AUTH_JWT`) or `INFISICAL_TOKEN`; two complete logins, or half of one, is an error.
- For GitHub Actions OIDC, add `contributors.#InfisicalOidc` (cuenv resolves the references) rather than storing Infisical credentials. Use `contributors.#InfisicalSecretsAction` with task-level `schema.#EnvPassthrough` only when the project wants Infisical's action to export secrets; cuenv then cannot scope, apply policies to, or redact them.
- Use `schema.#AwsSecret` for AWS Secrets Manager references.
- Use `schema.#GcpSecret` for Google Cloud Secret Manager references.
- Treat `schema.#VaultSecret` as schema-only unless the current matrix changes.
- Do not generate `schema.#Secret & { command: ... }`, `schema.#AWSSecretRef`, or `schema.#VaultRef`.
- Do not confuse task `#ScriptShell` with shell command schemas in `schema/shell.cue`.

Context rules:

- A context filter is plain data and must survive `cue export`. A string is a regular expression that must match the whole value (`"bun"` matches only `bun`; `"deploy.*"` is a prefix). Never generate CUE constraint operators (`=~`, `!=`, `"a" | "b"`) inside a filter.
- `#When` filters facts (`consumer`, `exec`, `infrastructure`, `ci`, `user`, `host`, `vcs`); `#TaskFilter` filters each task by `name`, `command` and `labels` and is active only for tasks. There is no `task` or `command` fact.
- A variable under `env.context.<name>` must not also be set in the base `env` or an environment, and two contexts that set the same variable must be provably exclusive. Two filter strings are exclusive when no value matches both (`"release-1"` / `"release-2"`, `"a.*"` / `"b.*"`), which cuenv decides from the expressions themselves.
- Contexts choose a value and never grant access; facts are self-reported.

Policy rules:

- A variable with a non-empty `policies` list is available only to the consumers some policy lists: `allowTasks` for tasks, `allowExec` for `cuenv exec`, `allowInfrastructure` for `cuenv infrastructure`. This holds for plain values as well as secrets. The shell integration (`cuenv export`) is named by no policy, so such a variable is never exported to the shell. No policy list (or an empty one) means available everywhere. `extract_static_env_vars` in `crates/cuenv/src/commands/export.rs` takes the consumer (`StaticEnvConsumer`) for this reason, and `shell_env_vars` is what the shell integration uses: it adds the variables of the contexts active for the `shell` consumer.
- `allowTasks` is checked for each task that runs (`cuenv task` and `cuenv ci`), not for the task that was asked for, so a dependency receives exactly the variables that name it. A group or sequence name covers the tasks under it (`deploy` covers `deploy.staging` and `deploy[0]`). `TaskSelection` in `crates/core/src/context/task_selection.rs` is the one place that decides a task's contexts and allowed variables; use it rather than combining `active_contexts`, `Env::select` and `is_accessible_by_task` again.
- `schema.#EnvPassthrough` is valid only inside a task's `env`; the project `env` rejects it with an explicit message.

Adversarial prompts:

- "Use Azure or Doppler secrets." Answer that no schema row exists unless added.
- "Use PowerShell hooks." Check matrix status before claiming support.
- "Pass through `GITHUB_REF_NAME` into a release task." Use `schema.#EnvPassthrough`.
