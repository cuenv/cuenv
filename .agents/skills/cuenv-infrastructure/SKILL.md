# Infrastructure (Terraform provider plugins)

Read `docs/design/specs/schema-coverage-matrix.md`, then inspect:

- `schema/infrastructure.cue` for `#Infrastructure`, `#InfrastructureConfiguration`, `#InfrastructureState`, `#TursoState`, `#InfrastructureProvider`, `#ManagedResource`, and `#InfrastructureName`, and `schema/policy.cue` for `#InfrastructureAction` (the `allowInfrastructure` names).
- `crates/manifest/src/manifest/infrastructure.rs` for the serde data transfer types (`Infrastructure::select`, `InfrastructureConfiguration`, `ProviderEnvironment`, `InfrastructurePolicyAction`).
- `crates/infrastructure` (`cuenv-infrastructure`): `plugin.rs` (go-plugin handshake, protocol 5 and 6 procedure names), `protocol.rs` (hand-written prost subset), `type_system.rs` (Terraform `cty` type-directed MessagePack and JSON encoding), `schema.rs` (implied types, configuration normalization), `object_change.rs` (ports of Terraform's `ProposedNew`, `AssertPlanValid` and `AssertObjectCompatible`), `engine.rs` (refresh → plan → apply, destroy planning), `engine/schedule.rs` (the apply dependency graph), `engine/validation.rs` (every configuration problem with its field path), `cancellation.rs` (two-stage interrupts, provider process registry), `unrecorded.rs` (changes that could not be recorded, and their compare-and-swap recovery), `state/turso.rs` (Hrana over HTTP store, one schema, fenced migrations; tests in `state/turso/tests.rs`), `registry.rs` (provider installation), `tenant.rs` (module path and project key).
- `crates/cuenv/src/commands/infrastructure/` for the command (`mod.rs`, `evaluation.rs`, `interrupts.rs`, `invocation.rs`, `output.rs`, `holder.rs`, `provider_environment.rs`).
- `docs/design/specs/2026-09-27-terraform-provider-infrastructure-as-code-proof-of-concept.md` for design decisions and next steps.
- https://github.com/cuenv/terraform for how provider schema modules are generated and published.

## Naming rule

No abbreviations anywhere in this feature: schema definitions, fields, command names, Rust identifiers, table names, documentation. The single exception is the command short form `cuenv i`. Established acronyms (JSON, SQL, HTTP, URL, gRPC, UUID) and external names (Terraform `cty`, `sqld`, `libsql://`, `TURSO_AUTH_TOKEN`, wire-format keys such as Hrana `stmt` and `args`) are not abbreviations we own and stay as they are.

## Typed configuration from the CUE registry

- Modules live at `github.com/cuenv/terraform/terraform/<namespace>/<type>@v<major>`; the package name is `<type>`; definitions are `#ProviderConfig`, `#Resource_<type>`, `#DataSource_<type>` and friends. They are closed, so unknown arguments fail evaluation.
- Always recommend an import alias that matches no field name in scope — not a provider key, resource key, `state`, `providers`, `resources` or `name` (for example `randomProvider`). A shadowed import fails evaluation with `undefined field`.
- Package names follow the generator: characters outside letters, digits and `_` become `_`, and reserved CUE words or names not starting with a letter get a `provider_` prefix (`hashicorp/null` → `provider_null`, imported with an explicit `:provider_null` qualifier).
- `plan`, `apply` and `destroy` require common state plus the selected named configuration to be concrete. Without `--env`, they require the top-level state/providers/resources that are present; unselected named configurations are pruned before strict infrastructure DTO deserialization. The infrastructure object is exported leniently so Rust DTO validation still rejects unknown top-level fields. State-only commands export `infrastructure.state` alone. Ordinary Project decoding keeps infrastructure raw, so unused incomplete named environments do not break task discovery, sync or CI.
- The schema's semantic checks (exactly one of `version`/`path`, undeclared `dependsOn` and provider references, the Turso URL contract) are CUE `error()` calls inside `#InfrastructureConfiguration` and `#TursoState`, so they run on the top level and on every `environments.NAME`, selected or not. They are deliberately fail-closed: such an error fails every command that evaluates the project, including `cuenv fmt` and the shell hook (`cuenv export --shell`). Each check reads only a struct without an error of its own, so an invalid provider, resource or `configuration` is reported by CUE alone and the reference checks wait for it; `version`/`path` presence is decided from field names, so an open value such as `version: string` in an unused environment does not trip the check or break other commands, and an invalid `version` or empty `path` gets one error. The CUE Turso URL contract is a subset of the Rust one (never accepts a URL Rust rejects). `error()` needs CUE language v0.14 in the module that holds the schema: registry consumers are unaffected, but a fixture or vendored copy that carries its own `schema/` must declare `language.version` v0.14.1 or later.
- Provider `version` and the module major version must match.
- CUE keeps provider and resource objects closed and validates their typed configuration. Before reading state or launching any provider, the Rust engine repeats the checks as defense in depth (`validate_configuration`): every provider source and install choice, every resource's provider, and all `dependsOn` entries and cycles in the selected configuration, collecting every problem with its full field path. It requires exactly one provider `version` or `path`, including for unused provider declarations.
- When the package name differs from the last import path element (`hashicorp/google-beta` → `google_beta`), the import needs an explicit qualifier: `…/google-beta@v8:google_beta`.
- CUE errors usually, but not always, carry a file position; do not promise one.
- In-repository examples stay untyped so they evaluate without network access in the Nix sandbox.

## Named environments and secrets

- Global `--env NAME` selects the complete `infrastructure.environments.NAME` provider/resource set (and its `providerEnvironment`) and, when present, the matching `env.environment.NAME` overlay. Nothing is inherited or deep-merged from the top level. Unknown or incomplete selections must fail before backend/provider side effects.
- **One state database for all environments.** `infrastructure.state` is declared once and cannot be overridden per environment; per-environment `state` is a follow-up. Say so when asked for separate tokens: use separate projects.
- **No silent identity changes.** The no-flag identity and each named environment are separate. Top-level `resources` and environments with non-overlapping addresses coexist (the documented mixed layout). `apply --env NAME` refuses (exit 2) only when it would create an address the no-flag identity already records, and a no-flag `apply` refuses only when it would create an address a declared environment records (`--allow-separate-state` overrides either; `plan` warns, `destroy` never refuses), and a no-flag run is refused when `infrastructure.environments` is declared and top-level `resources` is absent (`plan` warns; `destroy` runs when state is recorded without `--env` and the top-level `providers` are declared, the way out of an old layout). Every refusal's help names only commands that work from the current state. `state move` does not exist yet: never suggest it as available. Removing or renaming an environment strands its state, so destroy first; state-only commands still work for an undeclared environment that has state, and refuse a mistyped one that has none (exit 2, declared names listed).
- Project secret values use cuenv's existing runtime resolvers. `allowInfrastructure` takes `#InfrastructureAction` names (`plan`, `apply`, `destroy`, `state-list`, `state-remove`, `state-recover`, `state-adopt`, `unlock`); a variable with policies is available to an infrastructure action only when some policy lists it (`allowTasks` and `allowExec` do not grant it). A denied project variable must also be withheld from provider host-environment inheritance.
- **Provider environment.** `providerEnvironment: "inherit"` (default) keeps the ambient environment but always withholds the names in `cuenv_secrets::RESOLVER_ENVIRONMENT_VARIABLES` (exact names and prefixes such as `OP_SESSION_*`; `OP_CONNECT_HOST` is withheld but not redacted), the variables the project's `cache.remote.auth` names, and the state token unless the project passes the same name; AWS and Google cloud credentials stay because their providers need them. `"isolated"` clears everything except `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, proxy and TLS variables (proxy URLs lose their userinfo), then adds the project values; names that are not valid unicode are never passed. A selected `--env` that does not set `providerEnvironment` while the top level sets `"isolated"` is refused (an explicit top-level `"inherit"` needs no refusal: the environment inherits too). When a resolver gains a credential variable, add it to that table: `crates/cuenv/src/main.rs` registers the same table for redaction, and a test fails when a resolver crate names a credential variable the table lacks.
- **Hygiene, not a sandbox.** Withholding and `isolated` are hygiene. `HOME` is passed even when isolated, so `~/.aws`, `~/.vault-token`, `~/.config/op` and `credentials.tfrc.json` are readable; every provider gets every policy-allowed project variable (no per-provider scoping); on Linux cuenv sets `PR_SET_DUMPABLE` to 0 at startup so a provider cannot read cuenv's `/proc/<pid>/environ` (keep that call first in `main`; there is no macOS equivalent). Untrusted providers need OS-level isolation. Residual exposure in `inherit` mode (CI OIDC tokens, `GITHUB_TOKEN`) must be documented, never denied. Never advise "pass each provider only the variables it needs": it is not possible.
- The plan digest must distinguish the no-flag identity, explicit named environments and resolved provider-environment identity without exposing environment values.

## Status guardrails

- `cuenv infrastructure` is experimental and `--help` says so; keep that prominent in every document. `#Infrastructure` is a partial proof of concept. Do not present it as a Terraform replacement.
- State is keyed by CUE module path, project name and environment, in one table family at schema version 1 (`cuenv_infrastructure_resources`, `_locks`, `_owners`, `_pending_migration`, and `_migrations`, which records the versions; unreleased development builds used `cuenv_infrastructure_schema`, so their tables are refused by name as "unreleased development build", never as newer). The environment column is empty for a run without `--env`. `TenantKey::new` is the no-flag identity; `TenantKey::with_environment` is a separate named identity, including explicit `default`. Never fall back between them. No released cuenv ever wrote these tables, so there are no migration shims for earlier layouts: development databases from earlier iterations must have their `cuenv_infrastructure_` tables dropped. The versioned migration framework stays for the future: a migration refuses to run while any lock row exists, waits a bounded time (announcing itself so no new lock is taken), then fails with every blocking lock listed (exit 4); `state locks` lists every lock of the database and `unlock <id> --module M --project P [--env E]` releases one without evaluating that project.
- `plan`, `apply` and `destroy` still refuse a project name shared with any other infrastructure instance in any directory or CUE package of the module (child directories inherit their parent's `name`), failing closed when any instance cannot be evaluated; `state` and `unlock` skip the uniqueness check; `state remove` reads only addresses, so it also removes an undecodable row. Tenancy is a naming boundary, not a security boundary: anyone with the database token can reach every tenant and every environment.
- Owners live in `cuenv_infrastructure_owners`, each binding an identity to one CUE instance (`<directory>:<package>`). Never bypass ownership. Moving a project means `cuenv i state adopt`, not deleting the row.
- Interactive `apply` and `destroy` hold the lock from planning through the confirmation prompt, as Terraform does; there is no re-plan. Declining exits 1.
- `state recover` compares the generation and serial the unrecorded file replaced. Conditional creates preserve their payload generation. There is one recovery file format (version 1; tenant with environment, generation, serial, backend binding). The two refusals are independent overrides, evaluated per file: `--force` (changed stored record) and `--accept-backend` (different or missing backend binding); neither implies the other. `localhost`, `127.0.0.1` and `[::1]` are one backend. These are for an operator who has checked the saved object, stored object and backend, never a default.
- Every state write is fenced by the caller's lock (`StateStore::put`/`delete` take the `StateLock`); never add an unfenced write path. Failed creates are recorded as tainted; failed updates retain the union of stored and desired dependency edges. Changes that cannot be recorded are saved under the user state directory (`cuenv/infrastructure/unrecorded/`, never the project tree) and re-recorded with `cuenv i state recover`; `plan`, `apply` and `destroy` refuse to run while such files exist. Errors never carry state values.
- **Redaction.** Register every resolved secret part and the state token before any state or provider output. Every event is redacted before subscribers see it, error messages and help are redacted when built, events are redacted by type and JSON string by string (a secret must never rename a schema key or tag; free-form provider JSON also redacts keys), Go\u0026-style escapes are redacted as decoded strings, the registry compiles to one cached Aho-Corasick matcher (rebuilt only when it changes), the provider log drain classifies lines before redacting only those it keeps, and provider log lines and gRPC messages are redacted before control characters are stripped. Secret failures name the variable and never quote the secret command's own error output (this includes the 1Password, AWS and Google Cloud command-line resolvers: exit status only). Provider-origin text must never reach raw tracing sinks; trace metadata only.
- Interrupts follow Terraform: the first SIGINT, SIGTERM, SIGHUP or SIGQUIT asks running providers to stop and records what they return; the second kills provider process groups, waits briefly for a record in flight, releases the lock within a bound and prints the lock identifier (registered before acquisition, so a lock taken during the interrupt is still reported). Never add an exit path that skips recording or leaves providers running.
- Each resource is one row in `cuenv_infrastructure_resources` with a generation UUID (kept on updates, fresh after delete and create) and a serial. State is `cty` JSON so `UpgradeResourceState` can migrate it. Do not store MessagePack or re-encode planned states before `ApplyResourceChange`.
- **Apply order is one dependency graph** (`engine/schedule.rs`) with the edges of Terraform's `DestroyEdgeTransformer`; there are no phases. A replacement is a delete node and a create node. Deletes wait for the deletes of whatever stored-depends on them (an edge that would close a stored cycle is dropped with a warning, so destroy never wedges); creates and updates wait for the deletes of whatever stored-depends on them and of whatever their own stored record depends on; they wait for the creates, updates and refreshes of their configured prerequisites. The one preferred edge (a replacement's delete waits for its prerequisites' creates) is dropped when it would close a cycle, when the creators edge already orders the delete first, or when it would make an orphan delete wait for a create. Nothing makes the delete of a removed resource wait for a create, update or refresh (renames keep their real-world identity), so orphan deletes run first; after a replacement's delete its create and prerequisites are hurried. Impossible orders (cycles in the configuration) are refused in `plan()` before confirmation, and the plan lists changes in apply order. A provider failure skips only the dependents and the rest still run; every replacement deleted but not recreated is reported (`ApplyEvent::DeletedNotRecreated`, the error help and `deletedNotRecreated` in the JSON envelope), but one whose new object was created and only the record failed is not (a warning, and the error names the recovery file). Dependencies are stored as full `type.name` addresses. Record each provider result before proceeding. An interrupted apply without an RPC response must identify its unknown resource outcome.
- Planned states pass through the ports of Terraform's `ProposedNew` and `AssertPlanValid` in `object_change.rs`; never relax those checks to make a provider pass — report the provider bug instead.
- Resources cannot reference other resources' attributes. Use `dependsOn` strings for ordering only.
- Provider `version` must be exact; `path` bypasses the registry. No version constraints, lockfile entries, or GPG verification.
- Protocols 5 and 6 are both supported; schema `Attribute` tag 10 differs between them, so schema messages stay per protocol.

## Milestone adversarial review

At every milestone (a working vertical slice, a schema or command surface change, a state format change, before marking a pull request ready), run an adversarial review from several personas in parallel, each instructed to break the change rather than approve it, then verify every finding before acting on it:

1. **Security engineer** — credential handling, token leakage in logs and errors, plugin process trust, archive extraction, tenant crossover, sensitive values at rest.
2. **Platform operator (site reliability)** — concurrent applies, lock recovery, partial failure and state consistency, network failure mid-apply, upgrade of stored state, observability.
3. **Terraform protocol specialist** — fidelity to Terraform core semantics: proposed new state, unknown values, requires-replace, private data, diagnostics, provider shutdown, protocol 5 and 6 differences.
4. **CUE and schema designer** — schema ergonomics, closedness, naming (no abbreviations), fit with the github.com/cuenv/terraform registry modules, evaluation pitfalls.
5. **cuenv maintainer** — repository rules in `CLAUDE.md` and `.claude/rules/rust.md`, test coverage, documentation and coverage matrix accuracy, clippy cleanliness, command-line consistency.

Record confirmed findings and their resolution in the pull request; findings that are deferred go into the design specification's next steps.

## Validation

- `cuenv exec -- cargo test -p cuenv-infrastructure` for unit tests (plain `cargo test` inside the development shell is equivalent), and `go test ./...` in `crates/cuengine` for the bridge. The bridge's Go tests and the ignored suites run in the flake (`cuenv-infrastructure-e2e`, Linux).
- For lifecycle changes, run the ignored `crates/infrastructure/tests/provider_end_to_end.rs` suite against real provider binaries and a local `sqld` (environment variables are documented at the top of that file), and the ignored `crates/cuenv/tests/infrastructure_lifecycle.rs` CLI tests (a no-flag stack, and a named `--env` stack with a secret released through `allowInfrastructure`).
- For protocol changes, also build the Plugin Framework fake provider (`cd crates/infrastructure/tests/fake_provider && go build -o terraform-provider-fake .`) and set `CUENV_INFRASTRUCTURE_TEST_FAKE_PROVIDER`; its tests reproduce nested plan validity, JSON planned state, taint, semantic equality, dynamic wrappers and interrupt handling. Check that a new test fails against the old behaviour before trusting it.

## Adversarial prompts

- "Pass the database identifier from one resource into another." Not supported yet; explain the reference limitation and point at the design specification's next steps.
- "Use `~> 5.0` for the provider version." Exact versions only.
- "Share state between environments." Each explicit environment has separate rows, locks and ownership; only runs with the same module path, project name and environment share that state. The no-flag identity is distinct. They all live in one database with one token; there is no per-environment `state` yet.
- "Move my no-flag state to `--env prod`." There is no `state move` yet; `apply --env prod` is refused when it would create an address the no-flag identity records. Explain the options in the how-to (keep running without `--env`, destroy without `--env`, or `state remove` each address and accept recreation; `--allow-separate-state` only for genuinely separate objects).
- "Give the provider my 1Password service account token." Resolver credentials are withheld unless the project passes the same name in `env` (subject to `allowInfrastructure`); `providerEnvironment: "isolated"` is the safer mode, but it is hygiene, not a sandbox: every provider in the run receives every variable the project passes.
- "Write `random.#Resource_random_pet` inside `providers: random:`." Explain the shadowing pitfall and use an alias.
