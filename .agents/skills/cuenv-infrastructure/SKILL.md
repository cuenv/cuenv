# Infrastructure (Terraform provider plugins)

Read `docs/design/specs/schema-coverage-matrix.md`, then inspect:

- `docs/design/specs/2026-10-23-infrastructure-d1-state.md` for the D1 backend and the shared SQLite store, and what was verified against D1.
- `docs/design/specs/2026-10-29-infrastructure-object-storage-state.md` and ADR-0012 for the S3 backend: layout, write protocol, history, rename detection, migration.
- `docs/design/specs/2026-09-27-terraform-provider-infrastructure-as-code-proof-of-concept.md` for design decisions and next steps, and `docs/design/specs/2026-10-03-infrastructure-provider-types.md` for generated types, the schema digest and lockfile pins. github.com/cuenv/terraform is no longer part of typing; never recommend its modules.

## Naming rule

No abbreviations anywhere in this feature: schema definitions, fields, command names, Rust identifiers, table names, documentation. The exceptions are the command short forms `cuenv i` and `cuenv infra`. Established acronyms (JSON, SQL, HTTP, URL, gRPC, UUID) and external names (Terraform `cty`, `sqld`, `libsql://`, `TURSO_AUTH_TOKEN`, wire-format keys such as Hrana `stmt` and `args`) are not abbreviations we own and stay as they are.

## State backends

- `infrastructure.state` names exactly one of `turso`, `d1` and `s3` (the manifest type is an enum, `InfrastructureState`; use `credentials()` instead of matching when only the credentials matter). Change SQL stored-data behaviour in `state/sql.rs` only, so Turso and D1 cannot drift; a transport change belongs in `turso.rs` or `d1.rs`. Every store must pass `state/conformance.rs`.
- S3 state: every write is a conditional PUT on the ETag of the version whose lock it checked (GET → check lock → PUT `If-Match`; create with `If-None-Match: *`). Never add an unconditional write of `state.json`, never re-send a write blind after an ambiguous response (read the writer nonce back), and never recreate a missing `state.json` outside `state restore`. Errors never carry the endpoint or a credential. Only object stores offer `object_features()` (history, restore, rename, tenants listing, size, migration manifest, lock details); everything else goes through the `StateStore` trait.
- D1 binds parameters as text, and only in a request of one statement. Keep every statement that binds a parameter a single request, bind integers only where they are compared with or stored into a column (a text parameter compared with a literal is always greater), spell blob and nullable text parameters with `Dialect`, and inline locally computed integers as literals in multi-statement requests (migrations, the migration announcement).
- D1 reports SQL errors as HTTP 400 with code 7500; `d1.rs` reads the body before the status. Never quote a message of a request that carried state (`Disclosure::CodeOnly`), and never put the request URL in a message: transport errors drop it, and `D1::send` replaces the account and database IDs in Cloudflare's own messages.
- State credentials are configured, never read implicitly: `infrastructure.state.<backend>.token` for Turso and D1, `accessKeyId`/`secretAccessKey`/`sessionToken` for S3 (`#InfrastructureStateToken`: a string, `#Secret`, interpolation, or `#EnvPassthrough` with a required `name`), one set per state backend, which serves every environment (no per-environment overrides). S3 reads no ambient AWS credential chain. Do not reintroduce a default environment variable or a fallback to the process environment. A passthrough variable is always withheld from providers; state-only commands resolve no project variables.

## Typed configuration (generated provider types)

- A project-local `.infrastructure.cue` may select a separate infrastructure package with `schema.#InfrastructureLocator`, `directory`, `"package"`, and optional `projectPackage` (default `cuenv`). The directory is relative to the project and in the same CUE module; the project package and infrastructure package must differ. Commands load environment, policies, cache credentials and state identity from the owning project, then evaluate its separate package. Inline infrastructure remains supported but cannot be combined with a locator. Local provider paths remain relative to the owning project directory. Run `cuenv infra init` before loading infrastructure imports after a clone, including before `cuenv sync ci`.

- `cuenv infrastructure provider add <source>@<version>` installs the release, renders CUE from its gRPC schema into the CUE module's `cue.mod/gen/<hostname>/<namespace>/<type>` and pins version, schema digest and every platform's archive SHA-256 in the module's `cuenv.lock` (`[infrastructure_providers."<hostname>/<namespace>/<type>"]`, lockfile format version 5; lockfiles without the section stay at 4). It never evaluates or edits the user's CUE; it prints the imports. Nothing is published or fetched from a CUE registry, and `cue.mod/module.cue` is untouched. Commit `cuenv.lock` only: like managed codegen files, the generated directories are listed in a `cuenv infrastructure` `.gitignore` section and recreated by `cuenv sync` after a clone (never recommend committing them). Until then, any package that imports the generated types fails with `cannot find package`.
- Layout: the provider package is at `<hostname>/<namespace>/<type>` named `<type>_provider` (`-` → `_`), imported with a qualifier: `"registry.terraform.io/hashicorp/random:random_provider"`. Each managed resource has its own package at `.../resources/<resource type>` named after the type. Each data source has `.../data/<data source type>/data_source.cue`, exposing `#DataSource`, closed `#Configuration` and scalar `#Outputs`. One package per type keeps evaluation (and the shell hook) cheap for large providers.
- Use `providers: random: random_provider.#Provider` (closed; sets `source`, `version`, `schemaDigest` and types `configuration`) and `pet: random_pet.#Resource & {configuration: {...}}` (sets `type`; open for `provider` and `dependsOn`). `#Configuration` in each package is the closed definition behind them. Field names are Terraform attribute names. Required → `name!:`, optional and optional+computed → `name?:` (never `| null`), computed-only and write-only attributes are left out. Labels that are keywords or predeclared identifiers (`number`, `string`, `bool`, `list`, …) are quoted so they cannot shadow types.
- The `_provider` suffix exists because a field label shadows an import of the same name (`providers: random: random.#Provider` fails with `imported and not used`). The same applies to a resource key named like a resource package used inside `resources`; recommend another key or an import alias.
- `cuenv i plan|apply|destroy` compute the live schema's digest and refuse a provider whose digest differs from `schemaDigest` or the `cuenv.lock` pin, a configured version other than the pinned one, and an archive other than the pinned one for the current platform (`ProviderInstaller::ensure_pinned`). Unpinned, untyped providers behave as before.
- `cuenv infrastructure init` (also `cuenv infra init` or `cuenv i init`) installs pinned providers and regenerates their CUE types from `cuenv.lock` without evaluating project CUE or changing pins. It shares the restoration path with sync.
- `cuenv sync infrastructure [--check|--dry-run]` regenerates every pinned provider and the `.gitignore` section from `cuenv.lock` only (never evaluates CUE) and is part of plain `cuenv sync`. It only replaces or removes directories whose `provider.cue` starts with the generated-code header. `cuenv i provider remove <source>` deletes the directory and the pin. `cuenv sync lock` preserves the section.
- Generated resource and data source types accept top-level scalar output-reference descriptors and declare scalar `#Outputs`. Provider functions and ephemeral resources are not generated; local `path` providers cannot be added. One version per provider source per CUE module.
- The schema digest includes nonempty data source schemas; providers with no data sources retain their old digest. Existing pins made before data source support for providers that have data sources require `cuenv infrastructure provider add <source>@<same-version>`. Do not recommend sync to repair that pin: it verifies the locked digest rather than updating it.
- There is no typed example directory in the repository (its types would be gitignored, and the Nix sandbox cannot generate them); `crates/cuenv/tests/infrastructure_lifecycle.rs` `generated_provider_types_type_the_project` covers the typed path. `examples/infrastructure-random` stays untyped because the end-to-end tests swap in a local provider `path`.
- `plan`, `apply` and `destroy` require common state plus the selected named configuration to be concrete except recognized output placeholders/selectors. Without `--env`, they require the top-level state/providers/resources/data that are present; unselected named configurations are pruned before strict infrastructure DTO deserialization. The infrastructure object is exported leniently so Rust DTO validation still rejects unknown top-level fields. State-only commands export `infrastructure.state` alone. Ordinary Project decoding keeps infrastructure raw, so unused incomplete named environments do not break task discovery, sync or CI.
- The schema's semantic checks (exactly one of `version`/`path`, undeclared `dependsOn` and provider references, exactly one state backend, the Turso URL contract) are CUE `error()` calls inside `#InfrastructureConfiguration`, `#Infrastructure` and `#TursoState`, so they run on the top level and on every `environments.NAME`, selected or not. They are deliberately fail-closed: such an error fails every command that evaluates the project, including `cuenv fmt` and the shell hook (`cuenv export --shell`). Each check reads only a struct without an error of its own, so an invalid provider, resource or `configuration` is reported by CUE alone and the reference checks wait for it; `version`/`path` presence is decided from field names, so an open value such as `version: string` in an unused environment does not trip the check or break other commands, and an invalid `version` or empty `path` gets one error. The CUE Turso URL contract is a subset of the Rust one (never accepts a URL Rust rejects). `error()` needs CUE language v0.14 in the module that holds the schema: registry consumers are unaffected, but a fixture or vendored copy that carries its own `schema/` must declare `language.version` v0.14.1 or later.
- CUE keeps provider and resource objects closed and validates their typed configuration. Before reading state or launching any provider, the Rust engine repeats the checks as defense in depth (`validate_configuration`): every provider source and install choice, every resource's provider, and all `dependsOn` entries and cycles in the selected configuration, collecting every problem with its full field path. It requires exactly one provider `version` or `path`, including for unused provider declarations.
- CUE errors usually, but not always, carry a file position; do not promise one.

## Import and output references

- `cuenv i import <type.name> <provider-identifier>` imports one resource declared in the selected configuration. The identifier format belongs to the provider and is passed unchanged. Import uses the selected `--env`, provider environment, rename detection and tenant lock; it calls `ImportResourceState`, refreshes with `ReadResource`, then conditionally records the refreshed state at an absent address. It never calls `ApplyResourceChange`. Provider results containing zero or multiple resources, another type, structured identity, deferred results, or invalid refreshed state are refused. Import identifiers are registered for redaction before provider calls. Success prints the next environment-aware plan command.
- A top-level primitive destination argument in either `resources` or `data` can use `{fromResource: "cloudflare_zone.primary", attribute: "id"}`, `{fromDataSource: "aws_ami.base", attribute: "id"}`, or a direct CUE selector through `infrastructure.resources.primary.outputs.id` or `infrastructure.data.base.outputs.id`. Descriptors require exactly one source field plus `attribute`, with a `type.name` address. The source must be declared in the same selected configuration. For untyped declarations, declare an output as a bare `string`, `number`, or `bool` under `outputs`; generated resource/data types provide eligible outputs. The runtime lowers selectors to the same reference representation and infers dependencies across both namespaces. Source and destination provider attributes must have the same primitive type. Sensitive primitives are masked in plans; only known strings of at least four characters are registered for textual redaction. Nested or collection selection, refined output declarations, and expressions over outputs are unsupported.
- Known source outputs are included in planning. Outputs unknown until a producer is applied are resolved immediately before planning the consumer. Keep a provider-required replacement in the confirmed plan even while its reference is unknown; the schedule must include both delete and create halves. If only the final plan introduces a replacement, cuenv stops before mutating the consumer; the operator runs plan again after the producer is recorded. Final plans run only for references unknown at plan time, ignore `requires_replace` when there is no prior object (SDKv2 reports `ForceNew` on creates), and read source state upgraded to the current schema version. A final plan failing after a replacement's delete warns that the consumer was destroyed and not recreated.
- Import writes use the existing absent-record compare-and-swap and unrecorded-change recovery path. Check interruption before every later provider RPC or state mutation. A safe pre-mutation reference replan error skips only its dependents; unrelated operations can continue.

## Runtime data sources

- `infrastructure.data` maps names to `#DataSource`, with the same fields as `#ManagedResource`. These are read-only provider lookups, not managed resources. Data input/result values may contain collections, but `outputs` and references expose top-level scalars only.
- Each plan/apply invocation reads fresh data. Apply owns its planning reads across confirmation: do not reread an already resolved lookup just because the operator confirmed. Defer a lookup when any managed prerequisite changes, even if a referenced identifier is known, or a data prerequisite is deferred; run it after prerequisites complete during apply.
- `dependsOn` names managed resources only. Data edges are inferred from references. A deferred-read failure during apply skips dependents in the mixed graph; unrelated work can proceed. A data read failure during planning aborts the plan. Flatten managed ancestors reached through data into persisted managed dependency addresses so destroy ordering survives without data rows.
- Never persist data results as state rows or unrecorded-change recovery files. Values copied into managed resource arguments can still persist in managed state, including sensitive values; never claim that a data source keeps copied secrets out of state.
- Persist top-level sensitivity on managed records as `ManagedResource.sensitive_attributes: Vec<String>` (internal state, not a CUE field): union provider-schema, inherited-reference and stored names. Preserve the metadata through refresh, import, failed updates and recovery so a fresh-process destroy/orphan plan masks copied data secrets. An undecodable apply response must still preserve new marks on a retained prior record, with the normal recovery path if that metadata write fails; never accept malformed provider state. Unmapped historical marks conservatively mask current attributes, even without a schema-version change. Sensitive values remain plaintext in managed state and recovery files. Old records have no inferred provenance to reconstruct retroactively; data source support had not been released.
- Register known sensitive strings before validation/read RPCs and returned sensitive strings before response diagnostics, including keys within sensitive maps and best-effort extraction from malformed responses. If decoding fails, withhold unrestricted diagnostics. Mask all sensitive primitive types in plans, but textual redaction registers strings of at least four characters only, not numbers or booleans.

## Named environments and secrets

- Global `--env NAME` selects the complete `infrastructure.environments.NAME` provider/resource/data set (and its `providerEnvironment`) and, when present, the matching `env.environment.NAME` overlay. Nothing is inherited or deep-merged from the top level, including `data`. With named environments declared, a data-only top level is allowed only when the no-flag identity has no managed rows; otherwise retain the apply refusal and plan warning, with destroy still available. Without named environments, ordinary orphan deletion applies: a data-only apply can delete formerly managed resources omitted from configuration. Unknown or incomplete selections must fail before backend/provider side effects.
- **One state backend for all environments.** `infrastructure.state` is declared once and cannot be overridden per environment; per-environment `state` is a follow-up. Say so when asked for separate tokens: use separate projects.
- **No silent identity changes.** The no-flag identity and each named environment are separate. Top-level `resources` and environments with non-overlapping addresses coexist (the documented mixed layout). `apply --env NAME` refuses (exit 2) when it would create an address the no-flag identity already records, and a no-flag `apply` refuses when it would create an address a declared environment records (`--allow-separate-state` overrides either address-overlap refusal; `plan` warns, `destroy` never refuses). The environments-only layout also refuses no-flag apply and warns in plan: a data-only top level is an exception only when there are no managed rows in the no-flag identity. Adding a lookup must not bypass protection of existing no-flag managed state. `destroy` runs when state is recorded without `--env` and top-level providers are declared, the way out of an old layout. Every refusal's help names only commands that work from the current state. `state move` does not exist yet: never suggest it as available. Removing or renaming an environment strands its state, so destroy first; state-only commands still work for an undeclared environment that has state, and refuse a mistyped one that has none (exit 2, declared names listed).
- Project secret values use cuenv's existing runtime resolvers. `allowInfrastructure` takes `#InfrastructureAction` names (`plan`, `apply`, `import`, `destroy`, `state-list`, `state-remove`, `state-recover`, `state-pull`, `state-restore`, `state-migrate`, `state-rename`, `unlock`, and the retired `state-adopt`, which stays accepted for good); a variable with policies is available to an infrastructure action only when some policy lists it (`allowTasks` and `allowExec` do not grant it). A denied project variable must also be withheld from provider host-environment inheritance.
- **Provider environment.** `providerEnvironment: "inherit"` (default) keeps the ambient environment but always withholds the names in `cuenv_secrets::RESOLVER_ENVIRONMENT_VARIABLES` (exact names and prefixes such as `OP_SESSION_*`; `OP_CONNECT_HOST` is withheld but not redacted), the variables the project's `cache.remote.auth` names, and every state credential's passthrough variable unless the project passes the same name; AWS and Google cloud credentials stay because their providers need them. `"isolated"` clears everything except `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, proxy and TLS variables (proxy URLs lose their userinfo), then adds the project values; names that are not valid unicode are never passed. A selected `--env` that does not set `providerEnvironment` while the top level sets `"isolated"` is refused (an explicit top-level `"inherit"` needs no refusal: the environment inherits too). When a resolver gains a credential variable, add it to that table: `crates/cuenv/src/main.rs` registers the same table for redaction, and a test fails when a resolver crate names a credential variable the table lacks.
- **Hygiene, not a sandbox.** Withholding and `isolated` are hygiene. `HOME` is passed even when isolated, so `~/.aws`, `~/.vault-token`, `~/.config/op` and `credentials.tfrc.json` are readable; every provider gets every policy-allowed project variable (no per-provider scoping); on Linux cuenv sets `PR_SET_DUMPABLE` to 0 at startup so a provider cannot read cuenv's `/proc/<pid>/environ` (keep that call first in `main`; there is no macOS equivalent). Untrusted providers need OS-level isolation. Residual exposure in `inherit` mode (CI OIDC tokens, `GITHUB_TOKEN`) must be documented, never denied. Never advise "pass each provider only the variables it needs": it is not possible.
- The plan digest must distinguish the no-flag identity, explicit named environments and resolved provider-environment identity without exposing environment values.

## CI workflows

- `infrastructure.workflows` (`#InfrastructureWorkflows`) makes `cuenv sync ci` write, for each provider in `ci.providers` (only `github` so far), `<project>-infrastructure-plan.yml` (pull requests, plan, job summary, one pull request comment per project edited in place through `actions/github-script`, skipped for forks and cancelled runs) and `<project>-infrastructure-apply.yml` (`apply.on`: `push` to `apply.branch` by default with the job guarded to that branch, `tag`, `release` or `manual`; `apply.manual` adds `workflow_dispatch`; `apply.environment` sets the job's GitHub environment without setting `CUENV_ENVIRONMENT`). The code is `crates/cuenv/src/commands/sync/functions/github/infrastructure.rs`; it reuses the thin workflow emitter through `GitHubActionsEmitter::emit_command_workflow`, so the project's `ci` contributors install cuenv and set up secret providers (detected from base variables and from secrets inside `infrastructure`).
- The provider always comes from `ci.providers`; never make `infrastructure.workflows` add a provider, because that would also emit every `ci.pipelines` entry for it.
- Sync decodes only `infrastructure.workflows` from the raw value, never the whole configuration, so incomplete environments still do not block sync.
- Applies share one concurrency group (`${{ github.workflow }}`) and never cancel each other: a cancelled apply can leave the lock held. Keep it that way. Plans may be cancelled.
- Only the top-level configuration is planned and applied; do not claim named environments run in CI. Trigger paths come from the CUE loader (`cuengine::instance_sources`, Go `cue_instance_sources` in `crates/cuengine/sources.go`): the project's files, ancestor same-package files and transitive in-module imports, plus the project directory and `cue.mod/**`. Never fall back to directory guesses when the loader fails; sync fails instead.

## Status guardrails

- `cuenv infrastructure` is experimental and `--help` says so; keep that prominent in every document. `#Infrastructure` is a partial proof of concept. Do not present it as a Terraform replacement.
- State is keyed by CUE module path, project name and environment, in one table family at SQL schema version 2 (`cuenv_infrastructure_resources`, `_locks`, `_owners`, `_pending_migration`, and `_migrations`, which records the versions). The shared SQL store supports a transactional version-1-to-2 migration adding `sensitive_attributes` with an empty-list default and atomically renaming `state_json` to `resource_state_json`; provider state and private bytes are untouched, and migration 1 stays unchanged. The rename invalidates legacy projections: a version-1 reader that already passed its version check must fail closed if its old SELECT runs after migration. Never expose a compatibility view restoring that projection. Distinguish this supported version 1 from incompatible unreleased development layouts (including `cuenv_infrastructure_schema`), which remain refused by name as "unreleased development build", never as newer; those earlier layouts are not adopted. The environment column is empty for a run without `--env`. `TenantKey::new` is the no-flag identity; `TenantKey::with_environment` is a separate named identity, including explicit `default`. Never fall back between them. The migration framework fences upgrades: a migration refuses to run while any lock row exists, waits a bounded time (announcing itself so no new lock is taken), then fails with every blocking lock listed (exit 4); `state locks` lists every lock of the database and `unlock <id> --module M --project P [--env E]` releases one without evaluating that project.
- **Project names are unique** in the evaluated package, compared case-insensitively, for every project (one rule; do not add exceptions). `plan`, `apply`, `destroy`, `import`, `state migrate`, `state rename`, workspace-wide `cuenv sync` and `cuenv ci` refuse a duplicate and fail closed when an instance cannot be evaluated; the check lives in `cuenv_core::module` (`duplicate_project_names`). The SQL backends, whose key has no package, also keep the cross-package check (any instance with the same `name` and an `infrastructure` block, child directories included). `state list`/`pull`/`unlock` skip the module walk; `state remove`/`recover`/`restore` refuse a target in a directory the walk skips. Task discovery refuses a reused name. Tenancy is a naming boundary, not a security boundary: anyone with the database token or bucket credential can reach every tenant and every environment.
- There is no ownership gate. Taking the lock records the instance (`<directory>:<package>`) as the last writer (`cuenv_infrastructure_owners` for SQL, `lastWriter` in `state.json` for S3); it is information only, shown by `plan` and used by rename detection. `state adopt` is a no-op kept for one release. Never reintroduce a gate.
- S3 rename detection: before a tenant is created, `apply`/`destroy`/`import` refuse when state last written from this directory exists under an identity the configuration no longer declares and holds records or a lock; `state rename --from-*` moves it, `--new-identity` skips the check once. Another package in the same directory is evaluated, and a package that does not evaluate is a refusal, never an answer.
- `state migrate` copies to `migrateStateTo` (S3 only), fencing the source with a `migrated-<id>` lock; SQL migrations ignore and keep such locks, and `unlock` refuses them without `--migration-fence`.
- Interactive `apply` and `destroy` hold the lock from planning through the confirmation prompt, as Terraform does; there is no re-plan. Declining exits 1.
- `state recover` compares the generation and serial the unrecorded file replaced. Conditional creates preserve their payload generation. There is one recovery file format (version 1; tenant with environment, generation, serial, backend binding). The two refusals are independent overrides, evaluated per file: `--force` (changed stored record) and `--accept-backend` (different or missing backend binding); neither implies the other. `localhost`, `127.0.0.1` and `[::1]` are one backend. These are for an operator who has checked the saved object, stored object and backend, never a default.
- Every state write is fenced by the caller's lock (`StateStore::put`/`delete` take the `StateLock`); never add an unfenced write path. Failed creates are recorded as tainted; failed updates retain the union of stored and desired dependency edges. Changes that cannot be recorded are saved under the user state directory (`cuenv/infrastructure/unrecorded/`, never the project tree) and re-recorded with `cuenv i state recover`; `plan`, `apply` and `destroy` refuse to run while such files exist. Errors never carry state values.
- **Redaction.** Register every resolved secret part and the state token before any state or provider output. Every event is redacted before subscribers see it, error messages and help are redacted when built, events are redacted by type and JSON string by string (a secret must never rename a schema key or tag; free-form provider JSON also redacts keys), Go\u0026-style escapes are redacted as decoded strings, the registry compiles to one cached Aho-Corasick matcher (rebuilt only when it changes), the provider log drain classifies lines before redacting only those it keeps, and provider log lines and gRPC messages are redacted before control characters are stripped. Secret failures name the variable and never quote the secret command's own error output (this includes the 1Password, AWS and Google Cloud command-line resolvers: exit status only). Provider-origin text must never reach raw tracing sinks; trace metadata only.
- Interrupts follow Terraform: the first SIGINT, SIGTERM, SIGHUP or SIGQUIT asks running providers to stop and records what they return; the second kills provider process groups, waits briefly for a record in flight, releases the lock within a bound and prints the lock identifier (registered before acquisition, so a lock taken during the interrupt is still reported). Never add an exit path that skips recording or leaves providers running.
- Each resource is one row in `cuenv_infrastructure_resources` with a generation UUID (kept on updates, fresh after delete and create) and a serial. State is `cty` JSON so `UpgradeResourceState` can migrate it. Do not store MessagePack or re-encode planned states before `ApplyResourceChange`.
- **Apply order is one dependency graph** (`engine/schedule.rs`) with the edges of Terraform's `DestroyEdgeTransformer`; there are no phases. A replacement is a delete node and a create node. Deletes wait for the deletes of whatever stored-depends on them (an edge that would close a stored cycle is dropped with a warning, so destroy never wedges); creates and updates wait for the deletes of whatever stored-depends on them and of whatever their own stored record depends on; they wait for the creates, updates and refreshes of their configured prerequisites. The one preferred edge (the handoff edge) makes the create of a new resource, or the create half of a replacement, wait for the delete half of every replacement configured to depend on it: a replacement's old object is deleted before the creates of its new prerequisites (the old object may hold the identity the prerequisite takes, and is destroyed anyway); if such a create fails the replacement is left deleted and not recreated, reported, and created by the next successful apply. Updates are not held back, deletes wait only for deletes, and the edge is dropped if it would close a cycle. Nothing makes the delete of a removed resource wait for a create, update or refresh (renames keep their real-world identity), so orphan deletes run first; after a replacement's delete its create and prerequisites are hurried. Impossible orders (cycles in the configuration) are refused in `plan()` before confirmation, and the plan lists changes in apply order. A provider failure skips only the dependents and the rest still run; every replacement deleted but not recreated is reported (`ApplyEvent::DeletedNotRecreated`, the error help and `deletedNotRecreated` in the JSON envelope), but one whose new object was created and only the record failed is not (a warning, and the error names the recovery file). Dependencies are stored as full `type.name` addresses. Record each provider result before proceeding. An interrupted apply without an RPC response must identify its unknown resource outcome.
- Planned states pass through the ports of Terraform's `ProposedNew` and `AssertPlanValid` in `object_change.rs`; never relax those checks to make a provider pass — report the provider bug instead.
- Resources and data sources can reference top-level scalar outputs in either namespace with an exclusive `{fromResource, attribute}` / `{fromDataSource, attribute}` descriptor or a direct CUE selector through `outputs`. References infer ordering edges; explicit `dependsOn` names managed resources only. Output declarations are placeholders removed before provider configuration. Sensitive primitives are masked; registered strings of at least four characters are redacted. Nested and collection selection remain unsupported.
- Provider `version` must be exact; `path` bypasses the registry. Lockfile pins come only from `cuenv infrastructure provider add`. No version constraints or GPG verification.
- Protocols 5 and 6 are both supported; schema `Attribute` tag 10 differs between them (and `write_only` is 10 in protocol 5, 11 in protocol 6), so schema messages stay per protocol.

## Milestone adversarial review

At every milestone (a working vertical slice, a schema or command surface change, a state format change, before marking a pull request ready), run an adversarial review from several personas in parallel, each instructed to break the change rather than approve it, then verify every finding before acting on it:

1. **Security engineer** — credential handling, token leakage in logs and errors, plugin process trust, archive extraction, tenant crossover, sensitive values at rest.
2. **Platform operator (site reliability)** — concurrent applies, lock recovery, partial failure and state consistency, network failure mid-apply, upgrade of stored state, observability.
3. **Terraform protocol specialist** — fidelity to Terraform core semantics: proposed new state, unknown values, requires-replace, private data, diagnostics, provider shutdown, protocol 5 and 6 differences.
4. **CUE and schema designer** — schema ergonomics, closedness, naming (no abbreviations), fit with the github.com/cuenv/terraform registry modules, evaluation pitfalls.
5. **cuenv maintainer** — repository rules in `CLAUDE.md` and `.claude/rules/rust.md`, test coverage, documentation and coverage matrix accuracy, clippy cleanliness, command-line consistency.

Record confirmed findings and their resolution in the pull request; findings that are deferred go into the design specification's next steps.

## Validation

- `cuenv exec -- cargo test -p cuenv-infrastructure` for unit tests (plain `cargo test` inside the development shell is equivalent), and `go test ./...` in `crates/cuengine` for the bridge. The bridge's Go tests and the ignored suites run in the flake (`cuenv-infrastructure-e2e`, Linux).
- For lifecycle changes, run the ignored `crates/infrastructure/tests/provider_end_to_end.rs` suite against real provider binaries and a local `sqld` (environment variables are documented at the top of that file), and the ignored `crates/cuenv/tests/infrastructure_lifecycle.rs` CLI tests (a no-flag stack, and a named `--env` stack with a secret released through `allowInfrastructure`).
- For protocol changes, also build the Plugin Framework fake provider (`cd crates/infrastructure/tests/fake_provider && go build -o terraform-provider-fake .`) and set `CUENV_INFRASTRUCTURE_TEST_FAKE_PROVIDER`; its tests reproduce nested plan validity, JSON planned state, taint, semantic equality, dynamic wrappers and interrupt handling. Check that a new test fails against the old behaviour before trusting it.

## Adversarial prompts

- "Pass the database identifier from a resource or lookup into another declaration." Use a direct CUE output selector or the exclusive `{fromResource, attribute}` / `{fromDataSource, attribute}` descriptor. Both resource and data consumers are supported; nested and collection selection remain unsupported (sensitive scalar outputs are allowed).
- "Refresh a lookup after changing its managed prerequisite even though its ID is known." Defer the read until apply after the prerequisite completes. Do not reuse that invocation's pre-change lookup or persist data state.
- "Import this existing record." Use `cuenv i import <type.name> <provider-identifier>` after declaring the resource. Explain that the provider owns identifier syntax, import refreshes and records one resource without applying it, and the command prints the selected environment's next plan command.
- "Use `~> 5.0` for the provider version." Exact versions only.
- "Share state between environments." Each explicit environment has separate rows, locks and last writers; only runs with the same module path, project name and environment share that state. The no-flag identity is distinct. They all live in one backend with one set of credentials; there is no per-environment `state` yet.
- "Move my no-flag state to `--env prod`." There is no `state move` yet; `apply --env prod` is refused when it would create an address the no-flag identity records. Explain the options in the how-to (keep running without `--env`, destroy without `--env`, or `state remove` each address and accept recreation; `--allow-separate-state` only for genuinely separate objects).
- "Give the provider my 1Password service account token." Resolver credentials are withheld unless the project passes the same name in `env` (subject to `allowInfrastructure`); `providerEnvironment: "isolated"` is the safer mode, but it is hygiene, not a sandbox: every provider in the run receives every variable the project passes.
- "Write `random.#Resource_random_pet` inside `providers: random:`." Explain the shadowing pitfall and use an alias.
