# Tasks, Graph, Cache

Read `docs/design/specs/schema-coverage-matrix.md`, then inspect:

- `schema/tasks.cue` for `#Task`, `#TaskGroup`, `#TaskSequence`, params, inputs, outputs, cache, and captures.
- `schema/execution.cue` for shared command and script shapes.
- `crates/task-exec` (execution engine) and `crates/manifest/src/tasks` (DTOs), including `crates/manifest/src/tasks/params.rs` for task parameter models, `crates/manifest/src/tasks/retry.rs` for retry config, `crates/task-exec/src/graph/build.rs` for task graph construction, `crates/task-exec/src/graph/output_refs.rs` for output-ref dependency edges, `crates/manifest/src/tasks/resolver.rs` for task path resolution, `crates/task-exec/src/process.rs` for host process spawning/output/registry handling, `crates/cuenv/src/commands/handler/task_handler.rs` for CLI-to-request adaptation, and `crates/cuenv/src/commands/task` when behavior matters.
- `crates/task-exec/src/graph_advanced_tests/` for advanced graph regression coverage grouped by cross-project references, synthetic hooks, workspace setup, cross-project hooks, error/label/build-for-task coverage, and scale/edge cases.
- `crates/task-exec/src/scope.rs` for the task scope `cuenv task`, `cuenv ci` and `cuenv up` share: it follows `#project:task` dependencies into other projects, which are part of the graph only.
- `crates/cuenv/tests/cross_project_deps.rs` and `crates/cuenv/tests/cross_project_execution.rs` for CLI-level cross-project execution coverage, and `crates/cuenv/tests/ci_affected.rs` for the same under `cuenv ci`. Keep temporary repo/module setup and command execution on `Result` helpers instead of file-level unwrap/expect allowances.
- Task-related Cucumber BDD step definitions live under `crates/cuenv/tests/bdd_support/task_steps.rs`; keep task fixture creation and command execution on fallible `StepResult` paths instead of reintroducing unwrap/expect allowances, and keep new task behavior scenarios in that module instead of growing the root BDD runner.
- CLI task/exec integration coverage keeps the root runner in `crates/cuenv/tests/task_exec_integration.rs`; shared harness code and basic, examples, label-selection, and hermetic PATH scenarios live under `crates/cuenv/tests/task_exec_support/`. Keep the shared harness helpers fallible for tempdir creation, CUE module setup, PATH lookup, and cuenv command execution, and keep scenario setup on `Result` helpers for fixture writes, UTF-8 path arguments, ordered-output checks, and PATH-line lookup instead of reintroducing parent/module-level unwrap allowances or raw stderr skip messages.
- `crates/cuenv/tests/stress_tests.rs` for ignored large-graph CLI stress coverage. Keep graph mutation, dependency-edge wiring, parallel-group calculation, topological ordering, and task-position lookups on `Result` helpers instead of reintroducing file-level unwrap/expect or print suppressions.
- `crates/cuenv/tests/examples_dag_tests.rs` for example-project DAG coverage. Keep these tests on checked `Result` helpers for root discovery, manifest loading, graph construction, and CI/task lookups instead of reintroducing file-level unwrap/expect allowances.
- `crates/task-graph/src/graph.rs` for generic DAG primitives and ordering, `crates/task-graph/src/graph/analysis.rs` for affected-task and transitive-closure helpers, and `crates/task-graph/src/graph/resolver_build.rs` when group expansion or sequence ordering matters. Read-only graph data implements `TaskNodeData`; code paths that inject group-level or output-reference dependencies require `MutableTaskNodeData`. Keep affected-task external resolvers behind the borrowed `ExternalAffectedResolver` alias so graph analysis stays generic over task data, not resolver ownership.
- `crates/task-graph/benches/graph_benchmarks.rs` should propagate `GraphResult` through Criterion setup/measurement helpers instead of using benchmark-wide unwrap allowances.
- `crates/core/src/contributors/{model,context,engine,dag}.rs` and `crates/core/src/contributors/workspace.rs` when task contributor injection or auto-association affects the DAG.

Generation rules:

- Use explicit `schema.#Task`, `schema.#TaskGroup`, and `schema.#TaskSequence` in examples.
- Use CUE references in `dependsOn` instead of stale string examples when possible.
- Reusable or hidden task definitions preserve referenced task identity through CUE reference metadata, including unambiguous schema conjunctions; do not recommend JSON value matching as a fallback. Ambiguous conjunctions do not identify a task.
- Explain that output refs imply dependencies. `inputs: [{task: "build"}]` adds the implicit `dependsOn` edge AND expands to `build`'s declared `outputs` as path inputs, so the consumer's key is a function of what the producer built.
- Hashing the producer's *output content* (not its action key) is deliberate and matches Bazel/buck2: it gives early cutoff, so a producer that reruns and emits identical bytes leaves every consumer hitting. Never propose folding a dependency's action digest into the consumer — that is moon's coarser model and it destroys early cutoff.
- `dependsOn` alone contributes nothing to the cache key, which is Bazel semantics. Tell users to declare a dependency's output as an input when they consume it; directory isolation prevents a `dependsOn`-only task from reading that undeclared relative path.
- Cross-project `#ProjectReference` inputs are implicit execution dependencies (`#project:task`) as well as hashed inputs. `TaskScope` (`crates/task-exec/src/scope.rs`) loads the referenced project when a selected task reaches it, for `cuenv task`, `cuenv ci` and `cuenv up` alike, runs the producer first, and only then hashes/materializes the mapping, so a clean checkout does not require pre-existing producer outputs. The producer runs **in its own project**: its directory, its `env` (selected by its own contexts and policies, matched by the task's name within that project), its runtime, tools, hooks (CI) and runtime cache identity. It never sees the consumer's variables or secrets. It is graph-only: not listed, and not selectable by name or `--label` from another project. Every name inside it is qualified (`#project:` on dependencies, output-reference placeholders, their inferred dependencies and mapped-input producers). The input hasher is rooted at the **VCS workspace** when one exists (falling back to the CUE module), not the consuming project, so sibling CUE modules are reachable. A project resolves by `name` (the shallowest directory that carries it; listing names needs every directory of the module to evaluate, otherwise the task that names one fails with the reason) or by path: `../api` relative to the consumer, `/services/api` from the workspace root, canonicalized, inside the workspace, with no listing needed. However it is spelled, a project is one set of graph nodes. Patterns are prefixed before they reach the walker, so widening what is reachable does not widen what is walked.
- A path in `inputs` starts from one of three places: a plain string (this project), `<pkg>.#Files & {paths: [...]}` (another project, written through its import `content "<module>/content:cuenv"`), or `schema.#ModuleFiles & {paths: [...]}` (the module root). Recommend the file references for files outside the project instead of `../` strings, which cannot be matched against changes and will be rejected. The caller chooses the files; the other project declares nothing; no task runs and no dependency is added. `Input::Files` (`crates/manifest/src/tasks/inputs.rs`) is bound when a graph is built: `TaskScope` resolves the anchor through `ProjectSource::files_anchor`: the name is bound among the packages the reading project imports (`cuenv_ci::imports`, over `cuengine::instance_sources_with` records, decided by `cuenv_core::module::ImportedProjects::bind`), never by listing the module, so an unrelated directory that fails to evaluate cannot fail the task; a project not imported, a child directory that only inherits the name, another package or module and a duplicate name are diagnostics. `ProjectSource::directory_of` (module-wide) stays only for `{project, task}` references; `#ModuleFiles` anchors at the owner's module root and rewrites each path to a `MappedInput` with an `anchor`, staged where it lies. `crates/core/src/tasks/file_references.rs` checks every bound path (the `#AnchoredPath` rules, `.git` segments included, anchor inside the repository, no `.git`, symbolic link or nested repository in its literal prefix, at least one matching file); the cache hashes it with `WalkOptions::real_directories()` (links, nested repositories and `.git` left out) and checks every file lies under the anchor; the executor refuses an unbound reference. Every reader of inputs goes through `Input::patterns`/`Task::input_patterns`, which yields `InputPattern::Project` or `InputPattern::Anchored` and drops nothing. Must-match applies wherever a graph or `cuenv ci` affected detection reaches the task (before selection, `--all` included), never in `cuenv sync ci`. A reference cannot be optional; never spread or iterate its `paths`. `#Files` is a reserved definition of every `#Project`; a `#Base` has none (files beside a base are module files).
- The schema stamps every task, group, sequence member, service and image with its project (`cuenvRef: {kind, project, name}`) and every output ref with `cuenvProject`. `crates/core/src/module/node_checks.rs` runs before reference metadata names any dependency: a `dependsOn` entry, pipeline entry, matrix `task`, `watch.rebuild` entry or service/image dependency stamped by another project is removed and recorded under `Project.diagnostics` (`_cuenvDiagnostics`), as is a foreign output ref or a file reference without `paths`; `TaskScope::graph`, CI planning (`reached_problems`), the CI compiler (`reached_inputs`) and `cuenv up` raise them only for nodes they reach. Do not recommend `dependsOn: [content.tasks.build]` yet: cross-project task references through imports arrive in a later release.
- Mapped inputs live in one frame: `MappedInput.source` and `.destination` are both relative to the CUE module root and are rebased by where the module lies below the hasher root, so they resolve when the module is not the repository root (one the hasher cannot place is `HasherRootMismatch`, never dropped). A `{task}` input without `map` is staged where its producer writes it; an explicit `map` records and materializes `to` below the consuming task's project. `from`'s literal prefix bounds what is hashed and everything below it is reproduced under `to`. Consequences to state when asked: two inputs at one path are one input when content and executable mode are identical, and `InputCollision` otherwise (which file wins would be an ordering accident); a `map` that relocates a file on a task that runs in the workspace (`hermetic: false`, `sandbox: "none"`) is an error, because nothing would stage it; under `cuenv ci` a task with such a `map` runs in an execution root, every other task in the checkout; a group or sequence runs what its children depend on outside it first; a reference that cannot be followed fails only the task that uses it, with the reason.
- Task output ref ownership is split: `crates/core/src/tasks/output_refs/` keeps `model.rs` (placeholder parsing) and `extraction.rs` (raw CUE JSON rewriting and host passthrough markers) for module evaluation, while `crates/task-exec/src/output_refs/resolver.rs` resolves completed task output before execution.
- CLI task execution phase ordering lives in `crates/cuenv/src/commands/task/execution.rs`; named/label selection resolution lives in `crates/cuenv/src/commands/task/execution/selection.rs`; task-list rendering and format selection lives in `crates/cuenv/src/commands/task/execution/listing.rs`; interactive picker handoff lives in `crates/cuenv/src/commands/task/execution/picker.rs`; task help/detail rendering lives in `crates/cuenv/src/commands/task/execution/help.rs`.
- CLI task result and tree/detail rendering should not rely on crate-wide `expect_used` allowances. Keep infallible `String` formatting local to the renderer and handle real conversions explicitly.
- Host process spawning, captured/inherited output, process registry updates, and Unix process-group setup live in `crates/task-exec/src/process.rs`; keep that OS-specific `pre_exec` boundary out of task orchestration.
- Task cache write/hit input structs are copyable borrowed-state bundles, and input-directory digest insertion borrows the digest before cloning it into CAS nodes. Keep workspace path normalization borrowing its base path instead of taking a `PathBuf` by value.
- Tasks default to the directory containing the CUE file that defines the executable task body: `dir: {from: "definition", path: "."}`. Use `dir: {from: "definition" | "caller" | "module", path: "..."}` when imported/re-exported tasks need an explicit base. The bundled Rust helpers force `from: "caller"` so imported Cargo tasks run from the project that binds them.
- `TaskIndex` preserves the `#project:` separator for cross-project deps and canonicalizes only the task path. CI affected-task checks resolve cross-project task refs through canonical task indexes. Split refs at the first `:` only: `#project:deploy:preview` means project `project`, task path `deploy:preview`.
- Call out limitations for `timeout`, `retry`, `continueOnError`, group `maxConcurrency`, and hermetic filesystem behavior unless matrix status changes.
- `hermetic` accepts `bool` or `#Hermetic` (`{passthrough?: [...string], sandbox?: #Sandbox}`). `hermetic: false` is never cached (`CacheSkipReason::NonHermetic`) and is never sandboxed; `passthrough` names the host environment variables whose values enter the cache key.
- `#Sandbox` is `"dir" | "none"`, **defaulting to `"dir"`** — like Bazel (not buck2, which leaves local actions unsandboxed and relies on remote execution), cuenv sandboxes by default and makes opting out explicit. Under `"dir"` the executor materializes a unique per-invocation exec root under `<cache root>/exec/` holding verified copies of exactly the declared inputs, runs the task in its preserved relative working directory, records outputs there, and replaces only declared files/directories in the workspace. An undeclared relative read fails; an undeclared write is lost. Hard links are forbidden because mutating one would mutate the workspace. `crates/task-exec/src/exec_root.rs` owns it; `crates/task-exec/tests/sandbox_dir.rs` proves it.
- The action frame is the VCS workspace root (`ActionFrame` in `crates/task-exec/src/cache.rs`): input paths and the working directory are both workspace-relative, so the exec root mirrors the repository. Input *declarations* stay project-relative; only the internal frame is workspace-wide. Do not reintroduce a project-relative frame or a module-root fallback for the workdir — a task whose `dir` lies outside its project then sees its inputs at the wrong relative path.
- Input symlinks follow Bazel's source-file model (`crates/vcs/src/walker.rs`): a selected symlink is hashed as its target and staged as a regular file at the link's path, wherever a file link points. Globs descend through directory symlinks only inside the workspace (pnpm links yes, a `nix build` `result` no); an explicitly named path is followed wherever it leads. A dangling symlink errors only when selected; cycles are not followed. Never make an unrelated symlink fail hashing: under the default sandbox a hashing failure fails the task. The CLI builds its `WalkHasher` with `.excluding(<cache root>)`, so a cache store or exec roots inside the workspace are never hashed as inputs. Output symlinks remain rejected.
- Sandboxing is independent of result-cache eligibility. Tasks with no inputs use an empty root; `cache: mode: "never"`, task-local runtime env, `CUENV_CACHE=off`, and unavailable cache storage still run under `"dir"` once inputs resolve. Input-resolution failures error rather than silently exposing the live checkout.
- Stricter OS-level sandbox tiers remain absent until implemented.
- `hermetic: sandbox: "none"` is the opt-out to recommend for tasks that must touch the live checkout (installers, dev servers, codegen writing back into the tree).
- Secret-derived environment values NEVER enter a cache key as plaintext: the key is stored in the CAS as a `Command` blob and a remote cache uploads it. `Environment::set_secret` marks them and `action_environment` substitutes `cuenv-secret-fp:<hmac>` keyed by `CUENV_SECRET_SALT`. With no salt the task is not cached (`CacheSkipReason::SecretsWithoutCacheSalt`) — never suggest omitting the value instead, which would make two different credentials key identically.
- The action key records the CUE-declared environment plus declared `passthrough`, never ambient host variables (`HOME`, `USER`, `TERM`, `TMPDIR`, `XDG_*`). It also records timeout declarations, so a success produced under a longer timeout cannot bypass a shorter policy configured later. Recommend `env` for values a task needs and `hermetic.passthrough` only when the result genuinely depends on the host; explain that declaring a name partitions the cache by its value.
- Entries are salted with `cuenv_cas::ACTION_SEMANTICS_VERSION`, not the cuenv release version. Bump it only when execution semantics change; a release must not invalidate the cache. On the wire the salt is REAPI's `Action.salt`, spelled `cuenv/action-semantics/v<N>`.
- Messages are Bazel Remote Execution API v2 protobuf. `crates/cas/src/reapi.rs` is the only place cuenv's types meet the wire format; digests are SHA-256 over protobuf bytes, never JSON. The local CAS and action cache therefore hold byte-identical records to bazel-remote, buildbarn, BuildBuddy, NativeLink, EngFlow and Namespace. Bindings come from `bazel-remote-apis`, which ships pre-generated code, so no `protoc` is required to build cuenv.
- REAPI requires canonical ordering that protobuf does not give for free: environment variables by name, `output_paths` lexicographically, platform properties by name then value, directory children by name. `reapi.rs` enforces all four; do not bypass it by encoding a message directly. REAPI path names are UTF-8 strings, so Merkle construction rejects non-UTF-8 input and output names instead of using lossy conversion.
- Declared outputs go into REAPI's merged `output_paths`, not the deprecated `output_files`/`output_directories`, and are sorted, so declaring the same outputs in a different order still hits the cache.
- `cuenv-cas-remote` implements the REAPI transport: `RemoteCas` (CAS + ByteStream), `RemoteActionCache`, `RemoteClient` (Capabilities + auth), and `LayeredCas`/`LayeredActionCache` for read-through with local write-back. It is tested end to end against an in-process tonic server in `crates/cas-remote/tests/reapi_roundtrip.rs`.
- The transport is wired into `cuenv task` through `#Cache.remote` and `$CUENV_REMOTE_CACHE` as a read-through layer. Empty `$CUENV_REMOTE_CACHE` disables it. Generated CI does not configure it automatically.
- `Cas` and `ActionCache` are `#[async_trait]`. Keep them async; a synchronous trait cannot express a network store without blocking an executor worker thread.
- An unusable action-cache entry — unreadable store, undeclared or overlapping output paths, missing or unverifiable blobs — is a miss, never a task failure (`cache::lookup`). Only an unparseable task `cache.maxAge` errors.
- Remote availability failures degrade to local misses, and an unreadable or failing local store falls through to the remote (`LayeredCas`). A remote `Tree` whose directory names an entry twice is rejected (`merkle::validate_entry_names`) rather than partly materialized. `RemoteCas::get` verifies every fetched blob; corrupt or incomplete results are never materialized, and task execution replaces the unusable hit.
- `RemoteConfig` is read-only until `writable()` is called. The CLI never calls `writable()`: `upload` and `$CUENV_REMOTE_CACHE_UPLOAD` are reserved but forced off until strict filesystem and network confinement exists.
- Cache-hit streams and outputs are fetched and digest-verified into a workdir-local scratch directory before any workspace path is replaced. Every transient workspace directory (staging, projection, backup) is an `exec_root::ScratchDir` named with `cuenv_vcs::SCRATCH_PREFIX` (`.cuenv-scratch-*`); input hashing and output collection both skip them, so a concurrent task's scratch copies never become inputs or outputs. Cached output paths that escape the workdir or traverse symlink parents are rejected.
- Miss and hit output projection use staged, rollback-capable replacement. A failed task never projects partial outputs, and a successful result removes declared outputs it omitted so downstream tasks cannot consume stale artifacts.
- Every sandboxed retry gets a fresh verified execution root. Failed-attempt files never flow into a cached success. In inherited/streaming output mode result caching is disabled because that process path does not capture reproducible stdout/stderr bytes.
- There is no `cuenv cache` command surface yet.
- `CUENV_CACHE=off|read|write|read-write` overrides task-result cache mode for one run (the analogue of moon's `MOON_CACHE`). It only narrows a declared policy: each permission applies only when the task's own mode also grants it, so `write` records nothing for a task declared `read` and nothing is ever enabled for `never`. It never disables directory isolation.
- `collect_outputs` derives walk roots from each output pattern's literal prefix. Do not reintroduce a full-workdir walk; a task declaring `target/release/app` must not traverse `node_modules`.

Event surface (`cuenv-events`):

- `TaskEvent` covers `Started`, `CacheHit`, `CacheMiss`, `CacheSkipped { reason: CacheSkipReason }`, `Queued { queue_position }`, `Skipped { reason: SkipReason }`, `Retrying { attempt, max_attempts }`, `Output { stream, content }`, `Completed { success, exit_code, duration_ms }`, plus `GroupStarted` / `GroupCompleted` with counts.
- `Started` carries `task_kind: TaskKind` (`Task` / `Group` / `Sequence`) and `parent_group: Option<String>` for group correlation.
- `CacheSkipReason` variants: `EmptyInputs`, `NonPathRef`, `NoResolvedInputs`, `RuntimeEnv`, `Disabled { reason }`, `NeverMode`, `HasherRootMismatch`, `HashFailed { reason }`, `NonHermetic`, `UnportableWorkdir`, `SecretsWithoutCacheSalt`, `UnknownProject { project }`, `InputCollision { path }`. The enum is `#[non_exhaustive]`. `NonPathRef` now means only an `Input::Task` that manifest expansion could not resolve to concrete output paths.
- `SystemEvent::EventGap { skipped }` is synthesised by `EventReceiver` when the broadcast bus lags so consumers (TUI, JSON renderer) can surface a gap indicator instead of silently dropping events. Public enums are `#[non_exhaustive]`.
- `cuenv-events::register_secret(...)` / `register_secrets(...)` enroll values; `redact(str)` rewrites them to `*_*`. The CLI renderer applies this automatically to anything routed through its output path; direct command output should use `println_redacted`, `print_redacted`, `eprintln_redacted`, or `eprint_redacted`, which write through explicit stdout/stderr handles instead of raw print macros.
- `CliRendererConfig` owns plain terminal color/verbosity settings; spinner UI toggles live in `CliSpinnerConfig` so task progress rendering remains isolated from non-spinner logs.
- CLI task-event rendering and spinner integration live in `crates/events/src/renderers/cli/task.rs`; service-event output lives in `crates/events/src/renderers/cli/service.rs`. Category renderers should use the CLI renderer stdout/stderr helpers instead of raw print macros. Keep config-free categories as associated functions instead of adding placeholder `self.config` reads.
- Spinner interleaved output should go through `SpinnerRenderer::print_above`, which uses `indicatif::MultiProgress::println` to preserve active progress-bar frames instead of writing directly to stderr. Keep indicatif `{...}` templates as named constants in `crates/events/src/renderers/spinner.rs`.
- Trace acceptance tests in `crates/cuenv/tests/trace_acceptance.rs` should return `Result` from binary/root discovery, dry-run execution, DAG JSON parsing, and task lookup helpers instead of reintroducing file-level unwrap/expect, print suppressions, unused tracing helper modules, or unused dry-run fields.
- `ExecutorConfig::continue_on_error` makes `cuenv task` and library callers honour the same DAG semantics as `ci.pipelines[*].continueOnError` — dependents of a failing task get `task.skipped { DependencyFailed }` and independent siblings keep running. Panics / `JoinError` are still fatal.
- `cuenv-events` emits via a process-wide `EventSender` installed by `set_global_sender` at startup. The `emit_*!` macros and `cuenv_events::emit(category)` / `emit_with_source(source, category)` both go through it directly. `CuenvEventLayer` is retained as a public type so callers that emit via `tracing::info!(target: "cuenv::...")` still flow into the bus, but the in-tree macros bypass it. Its thin layer stays in `crates/events/src/layer.rs`; tracing field extraction, redaction, and typed event construction live in `crates/events/src/layer/visitor.rs`.
- The exported `emit_*!` macro definitions live in `crates/events/src/macros.rs`; crate-root hidden helpers remain available for `$crate` expansion and redacted print helpers.
- JSON event rendering should go through `JsonRenderer::render_to_writer` for testable JSON-lines output instead of raw print macros.

Adversarial prompts:

- "Run these tasks with maxConcurrency 2." State current executor limitations.
- "Retry a task three times." Check whether retry is implemented before recommending it.
- "Pass stdout from one task to another." Use task output refs and cite the example.
