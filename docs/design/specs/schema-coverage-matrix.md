# Schema Coverage Matrix

This matrix is the agent-facing source of truth for cuenv feature coverage. It is intentionally schema-first: every exported `#Definition` from `schema/**/*.cue` has a row.

Status values:

- `implemented`: schema, Rust implementation, docs, and examples are aligned enough for agents to recommend the feature.
- `partial`: schema exists and some implementation exists, but agents must call out missing fields, provider gaps, or command limitations.
- `schema-only`: schema exists but the current implementation should not be presented as usable.
- `legacy`: retained for compatibility or older docs, not the preferred surface.
- `internal`: helper type that agents should usually explain only when debugging the schema or implementation.
- `docs-misleading`: current docs or examples overclaim support and must be corrected before agents rely on them.
- `needs-decision`: ownership or intended user surface is unclear.

Provider dispatch note: built-in sync operations use the single crate-private
registry under `crates/cuenv/src/commands/sync/`. The statically typed CLI owns
argument parsing and passes a normalized `SyncRequest` to that registry. cuenv
does not expose a third-party sync-provider API. Runtime execution and secret
resolution remain on their existing task and resolver paths.

CLI-only note: cuenv reads `cue.mod/module.cue` only to warn when a module's
`github.com/cuenv/cuenv` schema dependency version differs from the running CLI.
`cuenv sync` never writes `cue.mod/module.cue`.

Docs site note: the cuenv.dev site is built with Nimbus
(`@cloudflare/nimbus-docs`) on Astro. The release pipeline's `docs.build` task
produces a static `docs/dist` (including the Pagefind search index) and
`docs.deploy` publishes it to Cloudflare Workers static assets with Wrangler;
there is no server Worker. On pull requests, the `docs-preview` pipeline's
`docs.preview` task uploads the same build as a `pr-<number>` Worker Preview
(`wrangler preview`); a `url` capture feeds the pipeline's "Docs preview"
annotation. Doc paths in this matrix use `.mdx` for pages that
render components or `:::` admonitions, which plain `.md` does not.

CLI-only note: module evaluation waits `CUENV_EVAL_TIMEOUT` seconds (default
60) for the Go bridge before failing with a timeout error that names the
variable. Invalid values are configuration errors; the variable has no schema
definition.

CLI-only note: on Unix, service session metadata with a zero controller PID or
one not representable as a positive platform PID is corrupt. Whole-session `cuenv down` rejects it without
signalling, and `cuenv up` preserves the directory for inspection.

Evaluation note: cuenv 0.57.3 pins the CUE fork at
`5a1f958250d657f19d94121d0070ddd1faca6805`, based on CUE 0.16.1,
and builds the bridge with Go 1.26. The fork shares typed references whose
target was declared with a definition of the type when the type's other
definitions cannot be unified with it, and shares forward references into
closed definitions. From cuenv 0.75.0 the fork is pinned at
`806b30344b62501771703f0c8e3f0be45d8010df`, which also shares a typed
reference into an imported package (`pkg.tasks.a`) when the field is final and
reached from the package root by regular fields; a chain of eight projects that
depend on imported tasks evaluates in about 7,000 unifications where four took
3.4 million. `dependsOn` on `#Task`, `#TaskGroup`, `#ContainerImage`
and `#Service`, `#Pipeline.tasks`, `#MatrixTask.task` and `#Watch.rebuild` are
typed with `#TaskNode` unions; strings and output references fail evaluation
at the entry. Regression coverage in `schema_project_base_tests.rs` includes
deep chains for each node kind, a dependency diamond, pipelines declared before
their tasks, and the dependsOn, pipeline and rebuild rejections. Export still
expands full dependency subtrees, so heavy fan-in is a separate performance
limit. The bridge also extracts unambiguous task references from schema
conjunctions, including reusable hidden definitions; it does not infer a target
for an ambiguous conjunction. See [the evaluation measurements](cue-recursive-sharing.md).

Infrastructure note: `cuenv infrastructure` (short form `cuenv i`) is
**experimental** (`--help` and the documentation say so). It evaluates the
project's selected `infrastructure` configuration, which must be concrete except
recognized output placeholders/selectors for `plan`, `apply` and `destroy` (only this command asks the bridge to
validate it through the generic `concretePaths` evaluation option; state-only
commands export `infrastructure.state` alone; other commands keep infrastructure
raw during Project decoding, so unused incomplete named environments do not
prevent task discovery, sync or CI). The schema's semantic checks (one of
`version` or `path`, undeclared `dependsOn` and provider references, exactly one
state backend, the Turso URL contract) are CUE `error()` calls applied to the top level and to every
`environments.NAME`, selected or not, so they fail every command that evaluates the project (`cuenv fmt` and the shell hook, `cuenv export --shell`, included), deliberately fail-closed; they need CUE language v0.14 in the module
that holds the schema (registry consumers are unaffected). The Rust engine
repeats them and reports structural problems with safe field paths, hiding map
keys and unknown labels. Infrastructure commands withhold unstructured CUE and
decoding details before provider sensitivity is known. Uniqueness of the
project name is checked through the bridge's generic all-packages scope with
failing instances treated as errors. State is keyed by the `module:` path in
`cue.mod/module.cue` (major-version suffix stripped), the project `name` and the
selected `--env` (empty without it), and for S3 state the CUE package too.
Migration uses conditional manifest writes and records its target baseline
atomically; rollback checks that baseline under a protected target lock. Stop
all source and target clients, restores, unlocks and other migrators throughout
migration, rollback and cutover: independent environment keys cannot be fenced
atomically. Operators attest distinct physical-store identities, and an
interrupted rollback or uncertain lock release may require manual reconciliation.
Project names are unique in the evaluated package without regard to case;
`plan`, `apply`, `destroy`, `import`, workspace-wide `cuenv sync` and `cuenv ci`
refuse a duplicate and fail closed on an instance that does not evaluate, and
the SQL backends keep their cross-package check. A named environment and the
no-flag identity are separate identities in one state backend (a per-environment `state` is a follow-up), and
cuenv refuses `apply --env NAME` only when it would create an address the
no-flag identity already records, and a no-flag `apply` only when it would
create an address a declared environment records (`--allow-separate-state`
overrides both; `plan` warns; `destroy` never refuses), and a no-flag `apply` of a project that declares only environments
(`destroy` is the way out of an old layout; `state move` is a follow-up). Converging runs lock, plan, confirm
and apply that same plan with lock-fenced writes, ordered as one dependency
graph; interrupts finish the resource in flight and release the lock. Text plans
open with a table of every resource with work (type, name, action, changed
attributes), end with per-action totals, and
show each change as a structural diff (nested values over several lines, only
what differs in an update, JSON strings compared as documents, colors on a
terminal unless `NO_COLOR` is set); the reviewed plan digest keeps its own fixed
compact rendering. `--yes`
(alias `--auto-approve`) is required without a terminal; exit code 4 means
locked, 5 other infrastructure failures. Typed provider, resource and data source
configuration comes from CUE packages that `cuenv infrastructure provider add`
generates from each provider's own schema into `cue.mod/gen`, pinned with a
schema digest and archive hashes in `cuenv.lock` and regenerated by
`cuenv infrastructure init` (also `cuenv infra init` and `cuenv i init`) or
`cuenv sync infrastructure`, without evaluating project CUE (see
`docs/design/specs/2026-10-03-infrastructure-provider-types.md`).

Native output selectors are resolved through what the evaluator bound, using
`cue/provenance` in the pinned CUE fork, before any provider change, and verified with
real output values during plan and apply. A scalar argument can carry an output or be
computed from several. Conditions, labels, indexes and defaults that read one are refused
(see `docs/design/specs/2026-11-03-infrastructure-nested-output-references.md`).

Runtime data sources (`infrastructure.data`, `#DataSource`) remain **partial**
and experimental. Plan and apply each read fresh results; apply retains its own
planning reads across confirmation. Reads defer if any managed prerequisite
changes (even with a known identifier) or a data prerequisite is deferred.
`dependsOn` names managed resources only; references infer edges across both
namespaces. Deferred-read failures during apply skip dependents in the mixed
graph while unrelated work can proceed; planning read failures abort the plan.
With named environments declared, a data-only top level is allowed only when
the no-flag identity has no managed rows; otherwise the apply refusal and plan
warning remain, and destroy is still possible. Without named environments,
ordinary orphan deletion applies: a data-only apply can delete formerly managed
resources omitted from configuration. Managed ancestors
are flattened through data sources for stored destroy dependencies. Data results
have no state rows or recovery files; values copied into managed resource
arguments can still persist in managed state. Data inputs/results can contain
collections, but output declarations and references remain top-level scalar-only.
Managed records persist `sensitive_attributes: Vec<String>` as the union of
provider-schema, inherited-reference and stored top-level sensitivity. This
metadata survives refresh, import, failed updates (including undecodable apply
responses) and recovery so fresh-process destroy/orphan plans mask copied data
secrets. Unmapped historical marks conservatively mask current attributes even
without a schema-version change. Shared SQL schema version 2 adds
the metadata through a fenced transactional migration from version 1, defaulting
old rows to an empty list and atomically renaming `state_json` to
`resource_state_json` without rewriting provider state or private bytes.
Migration 1 stays unchanged. The rename invalidates legacy SQL projections, so
a version-1 reader that passed its version check before migration fails closed
on a later old SELECT; no compatibility view restores that projection. Old
records have no inferred provenance to reconstruct retroactively; runtime data
source support had not been released. Values remain plaintext in managed state
and recovery files. Earlier incompatible development layouts are still refused.
Sensitive primitives are masked; only known sensitive strings of at least four
characters are registered for redaction, before validation/read calls and before
processing response diagnostics, including keys within sensitive collections.
Undecodable results withhold unrestricted diagnostics. Nonempty data source schemas participate in the
schema digest; no-data digests are unchanged. Existing older pins for providers
with data sources require `cuenv infrastructure provider add <source>@<same-version>`;
sync cannot repin them.

CI note: Tasks that run the repository flake (`checks.*`, `darwin.*`,
`cross.linux`) use the flake source list as inputs. `ci.flake-source-check` in the `sync-check`
pipeline compares exec-root and checkout derivations. Nix bootstrap consumers
realize the checkout's `.#cuenv` package on each runner and put its store path on
`PATH`; they never compare binaries, because the derivation is not
bit-reproducible. GitHub's release task builds portable artifacts separately
from the Nix-native package; both use `[profile.release]` (thin LTO, 16 codegen
units, `opt-level = "z"`). Hermetic tasks use cuenv's writable task `HOME`;
host `HOME` remains excluded. This repository's pull requests run only
`x86_64-linux` jobs; the `darwin` and `arm` pipelines run on pushes to `main` and
on demand. `cargo.build` cross-compiles `linux-arm64` on the x86 runner, because
a `runners.arch` entry names the job's runner, not necessarily its target's
hardware. `ci.github.execution: "direct"` runs a task without `cuenv task`, which
`cargo.build` uses so its jobs need no `build.cuenv` or 1Password token. The manual
`release-dry-run` pipeline runs those builds without publishing. The `checks`
group covers every `x86_64-linux` flake check except `cuenv`, which is the same
derivation as the package and is built, with its install-check smoke test, by the
`sync-check` pipeline's `nix build .#cuenv` bootstrap on every trigger of the `ci`
pipeline except a change to `cuenv-ci.yml` alone (a package build failure
surfaces as a failed `cuenv-sync-check`). `checks.cuetty` builds the four
cuetty checks in one job (their third-party crates compile once per profile and
their source is limited to the app, `crates/cuengine` and the CUE files the
catalog test reads), and `checks.infrastructure-e2e` also names
`cuenv-fake-terraform-provider` and `cuenv-numeric-interop`, which its suite is
built from. `cuenv-cue-bridge-test`, the Go bridge's `go vet` and test
suite, runs in `checks.clippy` (x86_64-linux), `darwin.clippy` (aarch64-darwin)
and `arm.cuenv` (aarch64-linux). Dependabot pull requests do not rebase
automatically, so release
commits do not start their CI while release binaries wait for x86 runners.

Flake source filters exclude Cargo `target` directories, including under the
fake Terraform provider. Cargo target artifacts therefore do not change the
derivations when tasks materialize the flake's declared input trees.

The root and Cuetty Nix formatting checks pass options for module-level import
grouping, lowercase hex literals and macro matcher formatting to the pinned
rustfmt. Each check probes that its formatter applies those options. The root
check also covers the standalone `tools/function-enum` workspace. Its sources
are included in the formatting and standalone Clippy derivations; `treefmt.toml`
is included in the formatting derivation. The root check requires treefmt's
Rust options to match the Nix checks.
The root, Cuetty and standalone `tools/function-enum` Clippy checks explicitly
enable wildcard-import and undocumented-unsafe-block lints for all targets.
`checks.cuenv-clippy` builds both the root workspace and the standalone tool,
using the tool's own Cargo lockfile.
The offline audit checks the pinned RustSec database and verifies it rejects a
known vulnerable fixture. It does not check for yanked releases: that check was
already ignored, and the sandbox has no registry index.
`ci.schema-docs-check` passes through `PATH` for the shell tools used by its
script, including on NixOS systems without a populated `/usr/bin`.

Repository CI timings and proposed optimizations are recorded in the
[2026-11-06 CI performance investigation](2026-11-06-ci-performance.md).
Non-release Nix matrices execute their original commands directly, retaining
task environment, outputs, and dependencies. CI installs upstream Nix 2.31.2
without OIDC and installs Cachix from the locked nixpkgs input. Terminal Rust
checks discard Cargo artifacts. Nix test checks share the `ci` profile with
debug information disabled and prepare dependencies with one target-matched
`cargo test --no-run` pass; production dependencies use one build pass and
Clippy uses metadata-only preparation. BDD failures produce a nonzero exit,
verified with an intentional failing scenario in its Nix check. Cuetty's test
check compiles its test profile directly instead of first building an unused
release application.
Nix-backed source installs and bootstrap package realization support
both daemon profiles and the upstream single-user profile. Infrastructure
dependency preparation explicitly stubs its auto-discovered integration test
targets before compiling them with Crane's dummy source. The four dependency
derivations are version independent: their dummy source pins every workspace
member's version, so a release does not rebuild any dependency. The Go bridge is
built from its Go sources alone with no tests, and its tests are a flake check.

CLI note: project discovery (`cuenv ci`, `cuenv sync`) accepts file attributes
such as `@extern(embed)` or `@if(tag)` before an `env.cue` package clause.

CI note: `schema.#GitHubConfig.trustedPublishing` supports `cratesIo` and
`cueRegistry`. The CUE Registry path is implemented by the GitHub contributor
and generated workflow action; it requires `id-token: write` and is intended
for production release pipelines.

Build-only note: the root and Cuetty app-local Nix flakes pin Rust `1.98.1`
with matching `rust-overlay` locks. This compiler update changes no schema,
CLI support status, or declared workspace MSRV. The infrastructure tests use
explicit String clones to satisfy this compiler's Clippy checks; build and
Clippy validation must still pass before review or release.
