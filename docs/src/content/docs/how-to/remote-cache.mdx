---
title: Remote caching
description: Share cuenv's task cache between machines with a Bazel Remote Execution API server
---

cuenv's task cache speaks the [Bazel Remote Execution API v2][reapi]. The
endpoint must provide ActionCache, ContentAddressableStorage, Capabilities, and
ByteStream services using SHA-256 digests. cuenv verifies those capabilities
during connection instead of assuming compatibility from a provider name.

[reapi]: https://github.com/bazelbuild/remote-apis

## Configuration

```cue
package cuenv

import "github.com/cuenv/cuenv/schema"

schema.#Project & {
    name: "my-project"

    cache: remote: {
        endpoint: "grpcs://cache.example.com:443"
        auth: bearerTokenEnv: "CUENV_CACHE_TOKEN"
    }
}
```

Reads fall through to the remote and whatever is fetched is streamed,
digest-verified, and kept locally, so the second read of a blob is local. A
remote action result is promoted into the local action cache only after all of
its streams and outputs have been verified and committed successfully.

## Uploads and strict confinement

`upload` defaults to `false`. When `upload: true` (or
`CUENV_REMOTE_CACHE_UPLOAD=true`) is set, cuenv keeps all ordinary CAS writes
strictly local and publishes to the remote cache only through a dedicated
post-run publisher after **all** of the following hold:

1. The task ran under validated Linux strict OS confinement (`sandbox: "strict"`
   or `sandbox: "auto"` without fallback), with network isolation enabled and
   either a verified read-only runtime image or a verified pinned Nix store
   closure.
2. The task exited with status `0` and all descendants were reaped.
3. Output projection into the workspace succeeded.
4. The task environment contains no project secrets.
5. The invoking project is authorized for remote publication.

The publisher uploads the `Command`, `Action`, stdout/stderr logs, output files,
and nested `Tree` leaf blobs before updating `ActionResult` last. Cache hits,
failed launches, network-enabled tasks, non-strict runs, and macOS prototype
runs never write to the remote cache.

### Provision a Linux runtime image or locked Nix runtime

There are two supported paths to qualify Linux strict runs for cross-runner
cache hits and remote publication:

- **Locked Nix runtime (`runtime: type: "nix"`):** When `CUENV_SANDBOX_RUNTIME_ROOT`
  is unset and the project uses a Nix runtime locked in `cuenv.lock`, cuenv
  resolves the transitive `/nix/store` closure of the task's environment via
  `nix-store --query --requisites`, verifies every store entry is immutable
  (non-writable, directly under `/nix/store`), bind-mounts **only** those
  `/nix/store` entries read-only (with `/bin/sh` and `/usr/bin/env` symlinked
  into the closure and no host `/usr`, `/bin`, `/lib`, `/lib64`, or `/etc`
  exposed), and folds a deterministic `nix.closure.digest` into the action key.
  This works on ephemeral GitHub and Namespace runners without a pre-mounted
  SquashFS/EROFS image.
- **Operator-provisioned SquashFS/EROFS image (`CUENV_SANDBOX_RUNTIME_ROOT`):**
  Mount an operator-managed SquashFS or EROFS image and set
  `CUENV_SANDBOX_RUNTIME_ROOT` to its absolute mount directory. Build the image
  with the tools, interpreters, and shared libraries used by the task at their
  sandbox paths. cuenv mounts the supported runtime paths from this image,
  including `/usr`, `/bin`, `/lib`, `/lib64`, and `/nix/store`, and includes
  their content digest in each action key. Use the same immutable image across
  runners that share results.

Commands resolve using the task’s path inside the mounted runtime. Linux strict
runs backed by neither a runtime image nor a verified Nix closure fall back to
the host runtime with invocation-scoped cache keys. Linux runners must permit
unprivileged namespaces and mounting the runtime in the sandbox. If the
capability check fails, `sandbox: "strict"` rejects the task and `sandbox: "auto"`
falls back to a directory sandbox.

## HTTP/REST protocol

In addition to gRPC (`protocol: "grpc"`, the default — including for existing
`http://` and `https://` endpoints), cuenv supports the Bazel HTTP/REST remote
cache protocol (`/cas/<sha256>` and `/ac/<sha256>`) when `protocol: "http"` is
set:

```cue
cache: remote: {
    endpoint: "https://cache.example.com/bazel"
    protocol: "http"
    auth: bearerTokenEnv: "CUENV_CACHE_TOKEN"
}
```

Any path prefix on `endpoint` and any `instance` are preserved ahead of `/cas/`
and `/ac/`. Note that `bazel-remote` ignores the HTTP instance for CAS blobs
and only namespaces ActionCache keys when configured to do so; do not rely on a
URL prefix alone for tenant isolation. Object stores (S3, GCS, R2) are
supported behind a proxy that implements the Bazel HTTP/REST cache contract.
Credentialed redirects are restricted to the configured origin.

HTTP file uploads stream from disk. gRPC uses ByteStream for blobs that
would exceed the negotiated batch size after accounting for request overhead.

## Environment overrides

CI usually should not hard-code an endpoint in CUE:

| Variable | Effect |
| --- | --- |
| `CUENV_REMOTE_CACHE` | Sets or replaces the endpoint. Empty **disables** the remote. |
| `CUENV_REMOTE_CACHE_PROTOCOL` | Sets or replaces the transport protocol (`grpc` or `http`). |
| `CUENV_REMOTE_CACHE_INSTANCE` | Sets the remote instance. An empty value clears it. |
| `CUENV_REMOTE_CACHE_UPLOAD` | `true`/`false` override for post-run publication (still gated on strict confinement). |
| `CUENV_REMOTE_CACHE_CREDENTIAL_HELPER` | Sets or replaces the Bazel credential helper executable (e.g. `bazel-credential-nsc`). |
| `CUENV_REMOTE_CACHE_CA_CERT` | Path to a PEM-encoded custom CA certificate bundle. |
| `CUENV_REMOTE_CACHE_CLIENT_CERT` | Path to a PEM-encoded mTLS client certificate chain (paired with `CUENV_REMOTE_CACHE_CLIENT_KEY`). |
| `CUENV_REMOTE_CACHE_CLIENT_KEY` | Path to a PEM-encoded mTLS client private key (paired with `CUENV_REMOTE_CACHE_CLIENT_CERT`). |
| `CUENV_CACHE` | `off`, `read`, `write`, or `read-write` — narrows every task's cache mode for one run. A permission applies only when the task's own mode also grants it. |

```bash
# Point at a cache the repository does not know about
CUENV_REMOTE_CACHE=grpcs://ci-cache.internal:443 cuenv task build

# Point at an HTTP/REST Bazel remote cache
CUENV_REMOTE_CACHE=https://cache.example.com CUENV_REMOTE_CACHE_PROTOCOL=http cuenv task build

# Turn the remote off without editing CUE
CUENV_REMOTE_CACHE= cuenv task build
```

An unreadable `CUENV_REMOTE_CACHE_UPLOAD` is ignored rather than treated as
true — a typo must not start publishing entries to a shared cache.

## Credentials and CI trust boundaries

Only the *name* of an environment variable or credential helper is written in
CUE, never a token:

```cue
cache: remote: {
    endpoint: "grpcs://cache.example.com:443"
    upload:   true

    // authorization: Bearer $CUENV_CACHE_TOKEN
    auth: bearerTokenEnv: "CUENV_CACHE_TOKEN"

    // CI trust-boundary separation for `cuenv sync ci`
    ci: {
        readSecret:       "CACHE_RO_TOKEN"
        writeSecret:      "CACHE_RW_TOKEN"
        writeEnvironment: "cache-write"  // GitHub Actions Environment
        writeQueue:       "cache-write"  // Buildkite secret-policy queue
        isolatedCacheDir: true
    }
}
```

Set exactly one of `bearerTokenEnv`, `header`, or `credentialHelper`. Use a
dedicated environment variable when using `bearerTokenEnv` or `header`.

### Bazel credential helpers and Namespace (`authMode: "ambient"`)

Providers that issue short-lived credentials through a Bazel-compatible
credential helper — including Namespace (`bazel-credential-nsc`) — or through an
OIDC step writing into `$GITHUB_ENV` can use `credentialHelper` and
`ci.authMode: "ambient"`:

```cue
cache: remote: {
    endpoint: "grpcs://cache.namespace.so:443"
    upload:   true
    auth: credentialHelper: "bazel-credential-nsc"
    ci: {
        authMode:         "ambient"
        isolatedCacheDir: true
    }
}
```

cuenv invokes `<helper> get` with `{"uri": "<endpoint>"}` on stdin and attaches
all headers returned in `{"headers": {...}}` (for example both `authorization`
and `x-nsc-ingress-auth`) on every gRPC and HTTP request, registering every
value for secret redaction.

In `ci.authMode: "ambient"`:

- `cuenv sync ci` does not require static `readSecret`, `writeSecret`,
  `writeEnvironment`, or `writeQueue`, and does not overwrite `CUENV_REMOTE_CACHE`
  or auth environment variables provisioned via `$GITHUB_ENV` (such as
  `nsc cache bazel setup --static -o json`).
- `cuenv sync ci` still gates `CUENV_REMOTE_CACHE_UPLOAD` to `"true"` only on
  protected triggers (`false` on pull requests, schedules, and manual runs) and
  still isolates `CUENV_CACHE_DIR` per trust level when `isolatedCacheDir` is
  enabled.
- Pipelines that already declare a GitHub Actions `environment` (for example
  `environment: "production"`) retain their environment without conflicting with
  `writeEnvironment`.

Both `cuenv task` and `cuenv ci` use the project’s remote cache. An external
dependency project uses the local cache. Cache credentials stay with the cuenv
process. Action keys, task environments, CI hooks, runtime and tool setup, and
bundled secret resolver commands omit these variables.

In `ci.authMode: "secrets"` (the default), configure GitHub’s `writeEnvironment`
with deployment restrictions for trusted refs and store the write secret in that
environment. A job declaring a different environment retains its existing
environment and uses the read-only cache policy; separate cache-writing build
jobs from deploy jobs (or use `authMode: "ambient"` with OIDC/credential helpers)
when a pipeline needs both cache uploads and a deploy environment.

Buildkite requires agent 3.106 or newer for step-level secrets. Configure the
write secret’s access policy for the trusted pipeline, refs, and `writeQueue`.
Trusted webhook builds must match an explicitly named branch or tag. Use
separate runners or isolate both processes and cache storage across trust
levels. Pull requests and other untrusted
triggers use `readSecret`, or disable the remote when the read secret is omitted.

If the named variable is unset or the credential helper fails, cuenv warns and
may continue with anonymous reads, but configured authentication never silently
becomes an anonymous writer. A missing token degrades the cache; it does not
fail the build. When a credential helper returns an RFC 3339 `expires` field,
cuenv caches the headers and automatically refreshes them 60 seconds before
expiry.

### Custom CA bundles and mTLS client certificates

For self-hosted clusters or workload mTLS (such as Namespace), configure PEM
file paths under `cache.remote.tls` (or via `CUENV_REMOTE_CACHE_CA_CERT`,
`CUENV_REMOTE_CACHE_CLIENT_CERT`, and `CUENV_REMOTE_CACHE_CLIENT_KEY`):

```cue
cache: remote: {
    endpoint: "grpcs://cache.example.com:443"
    tls: {
        caCertPath:     "/etc/ssl/custom-ca.pem"
        clientCertPath: "/run/mtls/client.crt"
        clientKeyPath:  "/run/mtls/client.key"
    }
}
```

Both gRPC (`grpcs://`) and HTTP (`https://`) endpoints support `tls`. Unpaired
or unreadable certificate/key files degrade cleanly to the local cache.

## Diagnostics and maintenance

Use `cuenv cache` to inspect, verify, and clean local and remote cache state:

```bash
cuenv cache status                      # Show local root + probe remote reachability
cuenv cache stats                       # Show local CAS/AC entry counts and disk usage
cuenv cache inspect <digest>            # Decode an action's command, env, platform, and input tree
cuenv cache diff <left> <right>         # Explain why two action digests differed (env, platform, inputs)
cuenv cache verify                      # Read-only digest and referential integrity check
cuenv cache verify --repair             # Remove corrupt blobs and dangling action entries
cuenv cache gc --max-size 10G --dry-run # Preview LRU/age eviction (preserves nested trees & grace window)
cuenv cache prune                       # Sweep unreferenced CAS blobs and stale tmp/ dirs
```

Garbage collection defaults to the selected project’s `cache.local.maxSize`.
Pass `--package` to select the CUE package or `--max-size` to override its limit.

All `cuenv cache` commands accept `--output json` for scripting. `gc` and
`prune` traverse transitive `Tree` references for every surviving `ActionCache`
entry and protect recently written blobs with a 10-minute grace window.
Destructive maintenance returns a busy error while a cache transaction is active.
Retry once the active cache work finishes.

## What happens when the cache is unreachable

Nothing fails. An unreachable endpoint, a rejected handshake, or a server that
does not offer SHA-256 digests all log a warning and fall back to the local
cache. A cache is an optimization, so a dead network makes a build slower, not
broken.

The one exception is integrity: every blob fetched from a remote is
digest-checked before its bytes reach your workspace. A server that returns
the wrong content for a digest is rejected outright rather than trusted.
