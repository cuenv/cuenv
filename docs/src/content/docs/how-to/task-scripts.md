title: Task Scripts
description: Run script directories as tasks, or embed scripts with CUE
---

Use inline `script` for short task-local glue. Move longer scripts into files
and embed them with CUE's native `@embed` attribute.

When a project already keeps a directory of scripts, list it in `scriptDirs`
and every script in it runs as a task, with no CUE per script.

## Turn a Directory of Scripts into Tasks

```cue
schema.#Project & {
    name: "my-project"

    scriptDirs: [{
        path:    "scripts"
        exclude: ["*.lib.sh"] // helpers sourced by other scripts
    }]
}
```

With `scripts/release.sh`, `scripts/report.ts` and `scripts/lint.py`, cuenv
writes `scripts.gen.cue` beside `env.cue`:

```cue
// Code generated by cuenv from scriptDirs. DO NOT EDIT.
// Any cuenv command rewrites this file when the scripts change.

package cuenv

scripts: {
	lint:    {file: "scripts/lint.py", interpreter: *"python3" | _}
	release: {file: "scripts/release.sh", interpreter: *"bash" | _}
	report:  {file: "scripts/report.ts"}
}
```

Commit the file. Each entry of `scripts` runs as a task of the same name:

```bash
cuenv task                       # lists them with their interpreter
cuenv task release -- 1.2.0 "notes with spaces"
```

How a file becomes a script:

- **Opt-in.** Nothing is scanned unless its directory is listed. Each entry is
  a directory relative to the project.
- **Which files.** Only files directly inside the directory, never in
  subdirectories. Dotfiles, names matching an `exclude` glob, and links or
  directories that resolve outside the project are skipped. A missing
  directory is skipped with a warning.
- **The interpreter.** The file's shebang (`#!/usr/bin/env bash`,
  `#!/usr/bin/env -S bun run`), else an extension only one interpreter uses:
  `.bash`, `.fish`, `.nu`, `.py` (`python3`). A file with neither, such as
  `README.md`, is not a script. A `.sh`, `.js` or `.ts` file without a shebang
  is listed, but running it fails as ambiguous until the project sets its
  `interpreter`: cuenv never guesses bash for `.sh` or Bun for JavaScript.
  Supported interpreters are `bash`, `sh`, `fish`, `nu`, `python`, `python3`
  (and versioned `python3.N`) and `bun`; a script whose shebang names another
  program, such as `node`, fails with that name.
- **The name.** `prefix` followed by the file name without its extension:
  `prefix: "s-"` makes `scripts/release.sh` the script `s-release`. `rename`
  names a file directly: `rename: {"make.ts": "makeTs"}`.
- **Clashes.** Two files that would get the same name, such as `make.sh` and
  `make.ts`, are both left out, and every cuenv command says so until one is
  renamed or excluded. A script named like a task declared in `tasks` fails
  when run and names both.
- **How it runs.** The interpreter runs the script path from the project
  directory: `bash scripts/release.sh`. Arguments after the task name are
  passed through unchanged, after one leading `--`; there is no `${param}`
  interpolation.
- **Caching.** Scripts run in the workspace and are never cached. A directory
  can opt into hermetic execution with the inputs, outputs and cache policy
  that needs; the script itself is always an input:

```cue
scriptDirs: [{
    path:     "codegen"
    hermetic: true
    inputs:   ["schema/**"]
    outputs:  ["generated/**"]
}]
```

The interpreter must be on `PATH` or provided by the project runtime. When it
is missing, the task fails naming the program; this holds for every task, not
only scripts.

### Add to a Script

The project adds fields to a script by name, in `env.cue`. A script takes the
fields of a task that make sense for a file: `interpreter`, `description`,
`params`, `dependsOn`, `hermetic`, `inputs`, `outputs`, `cache` and `labels`.

```cue
scripts: {
    // A TypeScript file without a shebang.
    report: interpreter: "bun"
    release: {
        dependsOn: [tasks.build]
        params: {
            positional: [{description: "Version", required: true}]
            notes: {description: "Release notes", default: ""}
        }
    }
}
```

With `params`, cuenv checks the arguments first, then passes positional ones
in order and named ones as `--name value` (a true `bool` as `--name`):
`cuenv task release -- 1.2.0 --notes "first cut"` runs
`bash scripts/release.sh 1.2.0 --notes "first cut"`. Without `params` every
argument is passed as given.

### Depend on Scripts

Tasks and pipelines reference a script as `scripts.<name>`, a CUE reference
that fails to evaluate when the script does not exist:

```cue
let _s = scripts

tasks: publish: schema.#Task & {
    command:   "echo"
    args:      ["published"]
    dependsOn: [_s.release]
}

ci: pipelines: default: tasks: [_s.lint, tasks.publish]
```

A script's own `dependsOn` takes tasks and other scripts. `cuenv ci` and
`cuenv sync ci` run scripts like any other task.

### Keeping `scripts.gen.cue` Current

Every cuenv command checks the file against `scriptDirs` and rewrites it when a
script was added, removed or renamed, before it evaluates the project again.
When a reference to a new script fails evaluation, cuenv evaluates `scriptDirs`
alone, which does not read the failing reference, rewrites the file and
evaluates once more. Outside CI, `cuenv ci` does the same before it starts. The check costs a
directory read per script directory.

- `cuenv sync scripts` writes the file explicitly; `--check` fails when it is
  stale or files clash, `--dry-run` shows what would change, `-A` covers every
  project of the module.
- When `CI` is set, nothing is written and a stale file fails the command, so
  CI runs what was committed.
- `CUENV_AUTOSYNC=0` turns the rewrite off.

The same per-command sync keeps [codegen](/how-to/codegen/) files and the
outputs of `.rules.cue` current; see
[automatic sync](/reference/cli/#automatic-sync).

See `examples/scripts` for a project with bash, Python, fish, Nushell and Bun
scripts.

## Embed a Script File

Directory layout:

```text
.
├── env.cue
└── scripts/
    └── release.sh
```

`env.cue`:

```cue
@extern(embed)
package cuenv

import "github.com/cuenv/cuenv/schema"

schema.#Project & {
    name: "my-project"

    tasks: {
        release: schema.#Task & {
            script:      _ @embed(file=scripts/release.sh,type=text)
            scriptShell: "bash"
            inputs:      ["scripts/release.sh"]
        }
    }
}
```

`@embed` keeps the configuration CUE-native while removing large shell bodies
from `env.cue`. List the script file in `inputs` so hermetic execution and
task-result caching know that changing the file changes the task.

## Keep Small Scripts Inline

Inline scripts are still useful for short, readable commands:

```cue
tasks: {
    version: schema.#Task & {
        script: """
        git describe --tags --dirty
        """
        scriptShell: "bash"
    }
}
```

Once the script needs branching, helper functions, or more than a few lines,
prefer an embedded file.

## Choose the Shell

`scriptShell` accepts the supported task script interpreters:

```cue
tasks: {
    generate: schema.#Task & {
        script:      _ @embed(file=scripts/generate.py,type=text)
        scriptShell: "python"
        inputs:      ["scripts/generate.py", "schema/**"]
        outputs:     ["generated/**"]
    }
}
```

For shell scripts, tune strict-mode options explicitly when the defaults are not
right for the script:

```cue
tasks: {
    smoke: schema.#Task & {
        script:      _ @embed(file=scripts/smoke.sh,type=text)
        scriptShell: "bash"
        shellOptions: {
            errexit:  true
            nounset:  true
            pipefail: true
            xtrace:   false
        }
        inputs: ["scripts/smoke.sh"]
    }
}
```

## Cacheable Scripts

For tasks that should reuse results, declare both the script and the files it
reads:

```cue
tasks: {
    docs: schema.#Task & {
        script:      _ @embed(file=scripts/build-docs.sh,type=text)
        scriptShell: "bash"
        inputs: [
            "scripts/build-docs.sh",
            "docs/**",
            "package.json",
        ]
        outputs: ["dist/**"]
        cache: mode: "read-write"
    }
}
```

Use `hermetic: false` only for tasks that intentionally need the live checkout,
such as dev servers and interactive debugging tasks.
