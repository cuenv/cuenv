## Context

cuenv’s shell integration spawns hooks asynchronously so developers can keep working while environment setup completes. The implementation at [crates/cuenv/src/commands/hooks.rs](https://github.com/cuenv/cuenv/blob/main/crates/cuenv/src/commands/hooks.rs#L238) uses prompt- or directory-change hooks (for example: `PROMPT_COMMAND` in Bash, `precmd`/`preexec` in Zsh, and `on-variable PWD` in Fish) to trigger the export flow on each prompt. These handlers are implemented to be safe and idempotent: when no work is required the export flow is a fast no-op.

This ADR depends on the workflow outlined in [rfc-0003-shell-integration-workflow-and-hook-lifecycle](/decisions/rfcs/rfc-0003-shell-integration-workflow-and-hook-lifecycle/).

## Decision

1. **Asynchronous Execution**
   - `cuenv env load` MUST execute hooks in the background using `HookExecutor::execute_hooks_background`, freeing the invoking shell immediately after scheduling.

2. **Prompt-hook handlers and lifecycle (current behaviour)**
   - Shell integration scripts generated by `cuenv shell init` register prompt/drive hooks that invoke the hidden export flow on prompt or directory change (for example: `PROMPT_COMMAND` in Bash, `precmd` hooks in Zsh, and `on-variable PWD` in Fish).
   - These handlers are safe and idempotent: the `export` path is implemented as a no-op when there is no work to do (no `env.cue`, no pending hooks, or no completed state to apply).
   - The implementation does not currently perform automatic deregistration of these handlers after a one-time execution; they remain installed to provide continuous integration across prompts. Implementing automatic deregistration (self-unload) is a desirable future enhancement but is not required for correctness today.

3. **Polling and session isolation**
   - Each initialized shell gets a fresh session identifier, including nested shells. CI uses a separate invocation identifier. A directory admits one active hook run at a time, while completed results are scoped to the session that produced them.
   - A shell runs a new hook against its own pre-overlay environment, so reloading a changed input does not repeatedly prepend values such as `PATH`. Changes to ambient environment variables that are not declared hook inputs require an explicit reload or a new shell session.
   - Zsh applies changes from its parent prompt or `cuenv shell refresh`; ambiguous sourced-file and non-cuenv function frames fail closed. Arbitrary tied variables are rejected. The `PATH`/`path` pair is supported when its backing array has no colon-containing elements and is neither empty nor a single empty element; leading and trailing empty elements otherwise round-trip. A nested shell without the parent shell's local backups fails closed.
   - `cuenv env status` and `cuenv env check` inspect the exact session's progress. A shell waiting for another session's active run does not consume that run's environment.

4. **Failure Handling**
   - Failed hooks MUST NOT inject environment variables (ties into ADR-0004). The CLI SHOULD surface diagnostic output indicating failure.
   - Failed executions will still attempt to clean up supervisor state. Shell-side handlers remain installed but are safe: subsequent prompt evaluations will run the `export` flow which will detect the absence of a completed state and act as a no-op.

5. **Directory changes, cancellation and recovery**
   - A permanent cross-process state lock protects each run's reservation and exact run identifier. Cancellation requests do not release a reservation until the worker has stopped and reaped its registered direct child. Stale workers cannot finish or cancel a later run.
   - Automatic cancellation and timeouts stop and reap the direct child. Descendants can continue running, including processes that detach or escape; configurations requiring complete non-overlap must avoid background descendants or drain them explicitly.
   - If a process crashes or a reservation cannot be reconciled, `cuenv env recover --list` shows its directory key, instance hash and run ID. After draining the old run and its descendants, an operator can pass those exact values with `--drained` to `cuenv env recover`. PIDs are diagnostic hints, not proof that a run has stopped. Drain older cuenv binaries before upgrading because they do not participate in this locking protocol. A project directory renamed or replaced during a run also requires draining before recovery.

6. **State snapshots, private results and permissions**
   - State files contain progress metadata rather than hook definitions, captured output, detailed errors or environment values. A supervisor receives its startup payload and source scripts through anonymous pipes. It keeps a completed result in memory and serves the exact session and run over authenticated local IPC; multiple readers can retrieve that generation. If the broker is absent after a crash or idle expiry, the cached result is unavailable and the session may run the hooks again. An IPC generation check protects retrieval, not later shell evaluation.
   - One process may capture at most 16 MiB combined across stdout and stderr. The encoded result for a run and the encoded supervisor startup payload each have a separate 16 MiB bound. A result that exceeds a bound fails before publication. At most 32 completed brokers may hold leases per configured hook state directory; capacity exhaustion is reported rather than silently sharing or publishing a partial result.
   - Each state save writes a separate temporary file in the state directory, then replaces the state file. On local filesystems supporting atomic replacement, readers see a complete old or new snapshot. Conditional state, cancellation and cleanup updates participate in the cross-process lock; a separate read followed by a save is not a transaction.
   - On Unix, cuenv creates state directories with mode `0700` and state files with mode `0600`. For an existing application-managed default directory, cuenv verifies the owner through an open directory handle and removes group and other permissions when neither group nor others can write to it. It rejects directories writable by others, symlinks, and directories owned by someone else. A custom state directory must already be owned by the current user and have no group or other permissions; cuenv reports an error without changing it. The state directory's parent must be trusted. On Windows, the directory and file inherit the configured filesystem access controls.
   - The private IPC endpoint authenticates the same local user; it does not isolate mutually hostile processes running as that user. Application state does not persist captured values, but paths and input hashes can be sensitive, and operating-system swap, core dumps, filesystem journals and backups are outside this guarantee.
   - On Linux, result brokers use abstract Unix sockets. Their leases record the network namespace, so a lookup or automatic cleanup from another namespace, or without a readable namespace identity, fails without restarting the hook. An operator can recover an exact stranded run after attesting that its processes have been drained, including when its former namespace no longer exists. An incorrect drain attestation can allow hook side effects to run again.
   - Saves flush file contents before replacement but do not synchronize the parent directory, so this contract covers process crashes rather than machine or power-loss durability.
   - Explicit drained recovery removes an exact legacy state's associated regular `<instance>_hooks.json` and `<instance>_config.json` files without following symlinks. Orphan files with no corresponding state cannot be attributed automatically: after draining all older supervisors, inspect and remove known obsolete payloads manually. Historical shared `/tmp/cuenv_supervisor.log` and `/tmp/cuenv_supervisor_err.log` files are also operator-managed; inspect ownership and file type before removing them. These actions do not erase prior copies in journals, backups or swap. State files larger than 16 MiB are refused; after draining old processes, oversized or unparseable legacy files require manual inspection and cleanup.

7. **Input stability**
   - Hook execution identity includes the declared input files. Before publishing a successful result, the worker hashes them again and fails the run if the inputs differ or cannot be read. Inputs must remain stable for the whole run: a final comparison cannot detect a change that was later reversed, or a change after the comparison.

## Consequences

- Shells remain clean after hooks execute, reducing surprises and resource leaks.
- Users can run commands immediately; environment injection happens when ready.
- Hook failures do not leave lingering handlers that would re-run or spam the user.

## Status

Accepted — behaviour live in the CLI and relied upon by shell integration scripts.

## Notes

Future shells (PowerShell, Nushell) MUST implement equivalent prompt-driven integration semantics. If automatic handler deregistration (self-unload) becomes a required UX or security property, a follow-up ADR should be produced to specify the contract and cross-shell implementation plan.
