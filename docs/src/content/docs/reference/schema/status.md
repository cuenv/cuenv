title: Schema status
description: Current implementation status for cuenv CUE schema definitions
---

The CUE schema is the first source of truth for cuenv features. The implementation status lives in [`docs/design/specs/schema-coverage-matrix.md`](../../../../../design/specs/schema-coverage-matrix.md), which has one row for every exported `#Definition` in `schema/**/*.cue`.

Agents and contributors must use the matrix before generating examples or answering feature-support questions. A schema definition can be real without being fully implemented.

## Status meanings

- `implemented`: safe to recommend with current docs and examples.
- `partial`: usable only with the documented limitations.
- `schema-only`: do not recommend as working behavior.
- `legacy`: avoid in new examples unless explaining compatibility.
- `internal`: implementation helper, not usually a user-facing feature.
- `docs-misleading`: current docs overclaim support and must be corrected.
- `needs-decision`: intended user surface is not yet clear.

## High-risk current gaps

- Secrets: `#ExecSecret`, feature-gated `#OnePasswordRef`, feature-gated `#InfisicalSecret` (Universal Auth, OIDC Auth or an access token; GitHub OIDC through the opt-in `#InfisicalOidc` contributor), feature-gated `#AwsSecret`, and feature-gated `#GcpSecret` are implemented; `#VaultSecret` is schema-only until a runtime resolver is registered. Project environment policies also gate `cuenv infrastructure` actions through `allowInfrastructure`, before secret resolution, and resolved secret parts are registered for redaction.
- Runtime and tools: Nix, devenv, GitHub, Nix, Rustup, URL, and OCI tool sources are implemented; container runtime is not complete. OCI runtime (`#OCIRuntime`) is partial: `cuenv sync lock` resolves digests and per-image `extract` paths into `cuenv.lock`, and the `#OCIActivate` hook (`cuenv runtime oci activate`) extracts those binaries and prepends them to `PATH`.
- Images: `#ContainerImage` is partially implemented: `cuenv build` lists image definitions and builds selected images with the local Docker CLI. Registry builds are pushed with Docker buildx; Dagger execution and downstream image output-reference resolution remain incomplete.
- Services: `cuenv up`, `ps`, `down`, `restart`, and `logs --follow` use persisted service session state; service-to-service dependencies are honored and selected service starts include their service deps; task dependencies in `services.*.dependsOn` run before service startup; image dependencies are recognized but selected image builds still fail fast until image execution backends are wired into service startup.
- Infrastructure (experimental): `#Infrastructure` remains partial. `cuenv infrastructure` (`cuenv i`) plan, apply, import, destroy, state and unlock drive Terraform provider plugins (protocols 5 and 6) with lock-fenced, per-resource state in one Turso or Cloudflare D1 database keyed by CUE module path, project name and selected environment. No-flag and named identities remain separate; selection replaces the complete `providers`, `resources`, `data` and `providerEnvironment` configuration without merging. The schema checks providers, managed `dependsOn` names, exactly one state backend and the Turso URL in every configuration; the Rust engine repeats validation for the selection. Apply follows a mixed resource/data dependency graph; managed-operation and deferred-read failures during apply skip dependent work, while planning failures abort the plan. Replacements deleted but not recreated are reported. Provider processes withhold cuenv's secret-resolver credentials (or, with `providerEnvironment: "isolated"`, everything outside a small allowlist). `cuenv infrastructure provider add` generates closed provider, resource and data source configuration types in `cue.mod/gen` and pins version, schema digest and archive hashes in `cuenv.lock`. Resource and data declarations expose scalar `outputs`; both can consume native selectors or exclusive `fromResource`/`fromDataSource` descriptors. Nested and collection selection is unsupported. Sensitive primitives are masked; textual redaction covers registered strings of at least four characters. Import refreshes and records one managed resource without applying it. Resource identity, `state move`, provider version constraints and typed `path` providers remain unsupported.
- Infrastructure data sources (experimental, partial): `#DataSource` under `infrastructure.data` uses the `#ManagedResource` declaration shape for read-only lookups. Plan and apply read fresh results per invocation; apply retains its own planning reads across confirmation and defers a read if a managed prerequisite changes (even with a known identifier) or a data prerequisite is deferred. `dependsOn` names managed resources only; references infer data edges, and managed ancestors are flattened through data for destroy ordering. Data inputs/results may contain collections, but references and `outputs` are scalar-only. Data results have no state rows or recovery files; values copied into managed arguments can still persist in managed state. With named environments declared, a data-only top level is allowed only if the no-flag identity has no managed rows; otherwise the apply refusal and plan warning remain, with destroy still available. Without named environments, ordinary orphan deletion applies: data-only apply can delete formerly managed resources omitted from configuration. Generated `data/<type>/data_source.cue` exposes `#DataSource`, `#Configuration` and scalar `#Outputs`. Nonempty data source schemas enter the digest while no-data digests remain unchanged: older pins for providers with data sources need `cuenv infrastructure provider add <source>@<same-version>`, not sync.
- Infrastructure state (experimental, partial): shared SQL schema version 2 uses a lock-fenced transactional migration from version 1 to add top-level `sensitive_attributes` metadata and atomically rename `state_json` to `resource_state_json`. Existing rows default to empty metadata; provider state and private bytes are unchanged, and migration 1 remains unchanged. The rename invalidates legacy SQL projections so a version-1 reader that passed its version check before migration fails closed on a later old SELECT; there is no compatibility view. The engine persists the union of provider-schema, inherited-reference and stored sensitivity through refresh, import, failed updates and recovery, allowing fresh-process destroy/orphan plans to mask copied data secrets. Old records lack inferred provenance and cannot reconstruct it retroactively; runtime data source support had not been released. Sensitive values still remain plaintext in managed state and recovery files. Earlier incompatible development layouts remain refused, distinct from the supported version-1 migration.
- Tasks: groups, sequences, params, output refs, caching, `timeout`, `retry`, `continueOnError`, and group `maxConcurrency` are real. Hermetic host tasks use directory isolation by default, including when result caching is disabled, but absolute host paths and the network remain reachable; symlinked inputs are followed and staged as regular files (Bazel's source-file behaviour), and output symlinks are rejected. `timeout` is host-backend only (rejected on the dagger backend, which cannot tear down its container on elapse) and kills the task's whole process group; a timed-out attempt is never retried.
- CI and release: GitHub CI sync is the strongest path; Buildkite sync/export is partial; GitLab export/sync is schema-only and sync rejects it with a configuration error until an emitter exists; config-driven release backends are not complete.
- Dagger: `runtime: #DaggerRuntime` is parsed but does not select the Dagger backend or supply its image, secrets or cache; tasks run in Dagger only through the legacy `config.backend` (`#BackendConfig`) and per-task `dagger` (`#DaggerConfig`) form.
- Validation strictness: with a module `language.version` before `v0.18.0`, the top level of a file that embeds `schema.#Project` is open, so a misspelled top-level field is ignored, as is a top-level typo in a `tasks`, `services` or `images` entry not written as `schema.#Task &` (or `#Service`, `#ContainerImage`), and a top-level typo in a `.rules.cue` file that embeds `rules.#DirectoryRules` the same way (`examples/env-basic/.rules.cue`). Every other declared field is checked. From `v0.18.0` the top level is closed too. `scripts/check-schema-compat.sh` (`cuenv task ci.schema-compat`) evaluates every example under CUE v0.15.1, v0.16, v0.17 and v0.18 and each supported language version, and requires those known gaps to stay accepted before `v0.18.0`.

Run `cuenv task ci.schema-docs-check` after changing schema, docs, prompts, examples, skills, or CLI surfaces.
