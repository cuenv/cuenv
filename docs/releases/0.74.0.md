# cuenv 0.74.0

## `cuenv ci` no longer skips work it cannot rule out

`cuenv ci` reported "No affected tasks" in several cases where a task's inputs had in fact changed ([#611](https://github.com/cuenv/cuenv/issues/611)). Selection now fails closed: whatever cuenv cannot show to be unaffected runs, and a warning says why. Some pipelines will run more than before. None of the changes below needs a configuration change.

### Inputs outside the project

- A task that depends on a task of another project is selected when that project's files change, even when `--path` leaves the other project out of the run ([#612](https://github.com/cuenv/cuenv/pull/612)).
- `cuenv ci` runs a task that reads the output of a sequence step (`{task: "release[0]"}`); it failed with "Task 'release[0]' not found".
- An input with a `..` segment, or an absolute input, can never match a changed file. Its task now runs whenever anything changed, with one warning per task. `..` inputs will be rejected once CUE-native references ship; the replacement arrives in the next release.
- A project name means the directory that declares it. A directory below a project inherits the project's name, and cuenv used to pick between them at random.

### One way to read an input

Hashing, affected detection and workflow path filters each read an input pattern their own way ([#613](https://github.com/cuenv/cuenv/pull/613)). These inputs were hashed and never matched a change, and now match:

- a leading `./`, as in `./bun.lock`;
- a brace glob, as in `src/{a,b}.txt`;
- whitespace around the pattern, as in `"src/** "`.

The empty input and `.` mean the project directory everywhere. An input is relative to its project, and a changed file is placed in a project by the project's exact directory in the checkout; a checkout named like one of its projects no longer shifts every path by one level.

A pattern that matches a changed file only when it is read from the repository root still selects its task for now. If the pattern selects nothing under its own project, cuenv warns that this reading is going away.

### Changes to CUE

A change to the CUE a project is built from now selects every task of the project's pipeline ([#614](https://github.com/cuenv/cuenv/pull/614)): the project's own `.cue` files, those of the directories above it in the same package, the packages it imports, what its `@embed` attributes read, and `cue.mod/`. Editing a root file every project inherits, or `cue.mod/module.cue`, runs every task of every project, deployment tasks included. Deleting the last file of the package in a directory above a project counts too, and `@embed` arguments are read as CUE reads them.

### Runs with nothing to compare

Affected detection needs a base to compare with, and cuenv used to guess the previous commit when it had none ([#616](https://github.com/cuenv/cuenv/pull/616)). A run without a comparable base now runs its whole pipeline and says so:

- GitHub: scheduled and manual runs, tag pushes, the first push of a branch, and a push whose previous commit cannot be compared. Merge queue runs keep precise detection.
- Buildkite: every build that is not a pull request.
- A CI system cuenv does not recognise, unless `--from` is given.
- A local run in a directory that is not inside a git repository.
- GitHub pull requests are compared in the checkout only when it holds the pull request: its head, or GitHub's merge of it. A `pull_request_target` run on the base branch asks GitHub which files the pull request changes, and runs everything if GitHub cannot say.
- A GitHub listing long enough to have been cut short (3,000 files for a pull request, 300 for a push) is not used as a comparison.

`--from <ref>` that yields no comparison is now an error that says whether the ref is missing, shares no history with `HEAD`, or lies past a shallow boundary.

### Pipelines and projects

- A run without `--path` skips projects that have no `ci` block or do not define the requested pipeline. If no project in scope defines the pipeline, the run fails and lists the pipelines that exist.
- Groups and sequences are followed on both sides of a dependency.

## Dependencies on other projects run in their own project

A `#project:task` dependency, and the dependency a `{project, task, map}` input implies, now runs under `cuenv ci` ([#617](https://github.com/cuenv/cuenv/pull/617)); it used to fail with "depends on missing task". Under `cuenv task`, `cuenv ci` and `cuenv up` the other project's task runs in its own directory, with its own environment, secrets, hooks and cache identity; it used to get the consuming project's environment, secrets included.

- The other project's tasks are part of the graph only and cannot be selected by name.
- A project can be named by name or by a path, relative to the project that writes it or from the module root. Affected detection reads both spellings.
- A task output without `map` is staged where its producer writes it; with `map`, below the consuming project. Identical inputs at one path are one input.
- **Breaking:** a `map` that relocates a file on a task that runs in the workspace (not in a sandbox) is now an error, because nothing would stage the file. Under `cuenv ci`, a task with such a mapping runs in an execution root and must declare its outputs.
- A project located by path is keyed `#/path:task` in output and errors, where it was `#../path:task`.
- `cuenv task <group>` runs what its children depend on in other projects first.

## A reserved name in task groups

`cuenvRef` can no longer be the name of a child of a task group ([#615](https://github.com/cuenv/cuenv/pull/615)). The next release writes that field on every group to say which project it belongs to. This release already reads it correctly, so the cuenv binary and the schema (`cue mod get`) do not have to be upgraded together.

## Regenerate your workflows

Run `cuenv sync ci` after upgrading. Derived path filters now cover every change that affects a task (apart from inputs with a `..` segment, which are emitted at the path they resolve to), in two shapes only: a path with `path/**`, or the directory a glob is rooted in with `/**`. A project's CUE sources are listed as `<dir>/*.cue`, for each directory that contributes to it and each directory above one. Workflows can start more often than before; `cuenv ci` still selects precisely once they have started. Any task without path inputs that a pipeline reaches makes the whole project a trigger. An absolute input or an invalid glob makes every change a trigger, since `cuenv ci` selects its task on any change.
