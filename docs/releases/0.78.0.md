# cuenv 0.78.0

## Upgrade notes

- **Task cache keys change once.** Two fixes change how task cache keys are computed:
  - Task inputs now leave out files that git ignores.
  - A task's environment is resolved before its key is computed.

  The first run of each cached task after upgrading misses the cache and stores a new entry. Older entries are not reused, and nothing needs to be cleared ([#648](https://github.com/cuenv/cuenv/pull/648), [#649](https://github.com/cuenv/cuenv/pull/649)).
- **Input globs no longer match gitignored files.** A task that relied on ignored files (for example `node_modules`, `target` or generated output) as inputs must now name that location explicitly, such as `node_modules/**` or an exact path. Naming an ignored location opts it back in ([#649](https://github.com/cuenv/cuenv/pull/649)).
- **Infrastructure recovery files name their run's lock.** Unrecorded-change files saved by this version record the lock identifier of the run that saved them. cuenv 0.77.x and older refuse these files, so run `cuenv infrastructure state recover` with 0.78.0 or later. Files saved by older versions are still accepted ([#659](https://github.com/cuenv/cuenv/pull/659)).

## Fixes

- **Remote cache integrity**: a corrupt blob from the remote cache is detected and no longer poisons the shared cache ([#647](https://github.com/cuenv/cuenv/pull/647)).
- **Tasks with `env` stay cacheable**: the task environment is resolved before keying ([#648](https://github.com/cuenv/cuenv/pull/648)).
- **Fail-fast stops sibling tasks**: when fail-fast aborts a run, the processes of sibling tasks are stopped instead of left running ([#651](https://github.com/cuenv/cuenv/pull/651)).
- **`state recover` keeps other runs' in-flight markers**: recovery removes only the in-flight marker of the run that saved the file. While a later run's change to the same address is in flight, recovery refuses the file instead of clearing that run's marker, which could have led a plan to create a resource twice ([#659](https://github.com/cuenv/cuenv/pull/659)).
- **Lock release is reported truthfully**:
  - A run whose lock release failed no longer says nothing was released ([#650](https://github.com/cuenv/cuenv/pull/650)).
  - On Turso and D1, a release whose response was lost is no longer reported as "lock already gone". It is reported as uncertain, and `unlock --force` fails in that case instead of saying the identifier matched no lock ([#661](https://github.com/cuenv/cuenv/pull/661)).

## Formal models

The protocols behind state locking, the task cache, infrastructure changes in flight, state migration, the SQL state backends and hook runs are now model-checked with Quint and TLC in CI (`specs/quint`, the `cuenv-quint-specs` flake check). The models found the bugs fixed in #659 and #661 ([#658](https://github.com/cuenv/cuenv/pull/658), [#660](https://github.com/cuenv/cuenv/pull/660), [#662](https://github.com/cuenv/cuenv/pull/662)).
