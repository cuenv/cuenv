# cuenv 0.75.0

Projects reach each other through CUE imports
([#611](https://github.com/cuenv/cuenv/issues/611)). A task depends on another
project's task by referring to it, reads the files that task builds through its
`outputFiles`, and reads another project's files, or the module's, through a
file reference. `..` inputs and `#ProjectReference` are gone.

**The CUE module of this release was not published**: `cue mod publish` refused
the module as untidy. Use cuenv 0.75.1 and its schema, which carry the same
changes.

**Breaking.** Upgrade the cuenv binary and the schema together:
`cue mod get github.com/cuenv/cuenv@v0.75.1`. The schema writes a `cuenvRef`
stamp on every task, group, service and image. A cuenv older than 0.74.0 reads
it on a task group as a child task and fails on every project with a group.
`outputFiles` exists only on this schema. Regenerate workflows with
`cuenv sync ci`.

```cue
import (
	"github.com/cuenv/cuenv/schema"
	content "github.com/acme/site/content:cuenv"
)

tasks: build: {
	command: "astro"
	args: ["build"]
	dependsOn: [content.tasks.articles]
	inputs: [
		"src/**",                                                          // this project
		content.tasks.articles.outputFiles,                                // what another project's task builds
		content.#Files & {paths: ["images/**"]},                           // another project's files
		schema.#ModuleFiles & {paths: ["bun.lock", "services/shared/**"]}, // files at the module root
	]
}
```

## Tasks of another project

- `dependsOn: [content.tasks.articles]` depends on `content`'s task, never on a
  task of this project with the same name. Under `cuenv task`, `cuenv ci` and
  `cuenv up` it runs first, in `content`, with `content`'s own environment and
  cache identity. A project of another package that carries this project's
  name (one vendored into `cue.mod/pkg`, say) is another project too: a
  reference to its task fails, as one to any project outside the module does.
- Every task carries `outputFiles`: its declared `outputs`, as an input of
  another task. Reading it also depends on the task, which must declare
  `outputs`. The files are staged where the producer writes them. Within a
  project, write `tasks.docs.build.outputFiles` rather than
  `{task: "docs.build"}`.
- A group can be depended on, but cannot be an input yet: list its tasks'
  `outputFiles`. A whole sequence of another project, or a step of one, cannot
  be depended on. A task or group used as an input is a CUE error, and cuenv
  adds a hint to write `.outputFiles`.
- Two projects that depend on each other's tasks are an import cycle. Move what
  both need into a third project.
- A task of another project cannot be reused as a task of yours, under any
  label: `tasks: lint: shared.tasks.lint` conflicts on the project stamp, with
  an error that does not name the stamp:

  ```text
  tasks.lint: 3 errors in empty disjunction:
  tasks.lint: 5 errors in empty disjunction:
  tasks.lint: conflicting values {command:"eslint",…} and […] (mismatched types struct and list):
  ```

  Write the task body once as a definition in a package that is not a project,
  and use it in every project that runs it. Each use is stamped with the
  project that uses it:

  ```cue
  // bodies/bodies.cue
  package bodies

  import "github.com/cuenv/cuenv/schema"

  #Lint: schema.#Task & {
    command: "eslint"
    args: ["."]
    inputs: ["src/**"]
  }

  // app/env.cue
  tasks: lint: bodies.#Lint
  ```

## Files of another project, or of the module

A file reference names files where they lie. The task that reads them chooses
them; the project that holds them declares nothing. No task of the other
project runs and no dependency is added. A file reference is hashed for the
cache key and staged where it lies under the directory sandbox. `cuenv ci`
compares it with changed files from its own directory: an article of `content`
changing selects `app`'s task under `cuenv ci --path app`. `cuenv sync ci`
turns it into workflow path filters.

- Every path must match at least one file wherever a graph or affected
  detection reaches the task, including `cuenv ci --all` and runs with nothing
  to compare. A rename in the other project is an error for the task that reads
  it, never a silently smaller set of inputs. `cuenv sync ci` does not check
  this. A reference cannot be optional: a glob that is legitimately empty at
  times is an error for its readers then.
- Paths are relative to their anchor and stay inside it: no `..`, `.` or empty
  segment, no leading `/`, no surrounding whitespace. No path reads the
  repository's metadata: a `.git` segment, in any letter case, is rejected.
- A file reference never follows a symbolic link or enters a nested repository
  (a submodule, a worktree). Under a glob they are left out, and a path through
  one is an error.
- A `#Base` has no `#Files`; files beside a base are module files.
- `#Files` is a reserved definition of every project: a project that defines
  its own `#Files` fails to evaluate.
- A file reference without `paths` (`inputs: [content.#Files]`) is an error of
  its task only.
- At language version `v0.18.0` a base is written `schema.#Base...`. Embedding
  `schema.#Base` there closes the package and rejects every child's `name`.

Never spread a reference: `[..., ...content.#Files & {paths: [...]}]` and
`[..., ...content.tasks.x.outputFiles]` are valid CUE, but they copy bare
strings, which are paths of the consuming project, and drop the reference.

## Binding a project

A project name is bound among what the referring project imports, directly or
through another package, and nowhere else. cuenv no longer evaluates every
directory of the module to follow a dependency, so a directory that fails to
evaluate cannot fail a task that does not import it. A reference fails the task
that holds it, saying why, when its project:

- is not imported, even when the module has a project of that name or another
  project of the same run imports one;
- is imported from a child directory that only inherits its `name` (import the
  project's own directory);
- declares another CUE package than `cuenv`;
- comes from another CUE module.

## `cuenv ci` and `cuenv sync ci`

- `cuenv ci` follows dependencies on other projects' tasks into the producer.
  A dependency that does not bind fails the pipeline before any task is
  selected.
- A task whose only inputs are other tasks' `outputFiles` is affected, and
  triggered, through those tasks, instead of on every change.
- Trigger paths from `cuenv sync ci` follow dependencies into the producer: its
  inputs and file references, or its directory when it has no inputs. They go
  on through the producer's own dependencies, its own tasks and tasks of the
  projects it imports. An input `cuenv ci` cannot compare with changes (an
  absolute path, an invalid glob), in the producer or in a file reference, makes
  every change a trigger, since `cuenv ci` selects the consumer on any change.
- A thin workflow runs these dependencies inside `cuenv ci`. A workflow that
  runs each task in a job of its own (expanded and release pipelines, matrix
  tasks) cannot run a task of another project: `cuenv sync ci` refuses to
  generate one whose tasks depend on one, directly or through a group that
  holds them, and says to use `mode: "thin"`.
- In a job-per-task workflow, a group's `dependsOn` now reaches every task
  beneath it: a member's job waits for the group's dependencies in the same
  project, which were left out of the workflow before.
- `cuenv ci` names a failing task without its file and line: its evaluation
  does not collect source positions.

## Breaking changes

- **`..` inputs are rejected.** A string input with a `..` segment is a CUE
  error (`tasks.build._cuenvInputCheck."../content/articles/**": an input
  cannot leave the project directory`), and cuenv appends its path from the
  module root. Import the project that holds the files and write
  `<pkg>.#Files & {paths: [...]}`, or `<pkg>.tasks.<name>.outputFiles` for
  files a task builds. For files outside every project write
  `schema.#ModuleFiles & {paths: [...]}`, with paths from the module root.
  Nothing above the module root can be named. On an older pinned schema cuenv
  refuses the task, with the same rewrite.
- **`#ProjectReference` is removed**, with the `{project, task, map}` input,
  the `#project:task:path` and `#project:task` input shorthands, and
  path-shaped project references (`../content`, `/content`). Import the project
  and read `<pkg>.tasks.<task>.outputFiles`, which also depends on the task.
  Nothing relocates another project's outputs: read them where they are built.
  On an older pinned schema that still lets these through, the task that holds
  one fails, saying what to write; none is ever read as a task of this project.
- **A root file is no input of a project.** A changed file outside a project is
  no longer compared with that project's patterns from the repository root:
  - a pattern that selects nothing under its project (`shared/**` in `app`,
    with `shared/` only at the root) and matched only a root file now fails the
    `cuenv ci` run, saying to write
    `schema.#ModuleFiles & {paths: ["shared/**"]}`;
  - a root file named like an input of a project (`package.json`, `src/**`) no
    longer selects that project's tasks. Add `schema.#ModuleFiles` if a task
    does read the root file.
- **`#TaskOutput` is no longer the default arm of `#Input`**, and is closed: an
  object with any other field is no task output.
- `outputFiles` is a reserved field of every task, and `cuenvRef` of every task
  group: no child of a group can be called `cuenvRef`.
- An image that reads a task's `outputFiles` or outputs (`{task}`) is refused
  by `cuenv build` and `cuenv up`: nothing would stage them for the build.
- Rust API: `Input::Project`, `ProjectReference`, `Task::task_ref`,
  `Task::from_task_ref`, `Task::iter_project_refs`,
  `TaskCacheConfig::project_roots`, `ExecutorConfig::sandbox_project_roots` and
  the path-shaped `ProjectSource` methods are removed. `ProjectSource` binds a
  project with `imported_project`. The CI IR task gains
  `external_dependencies`.

## Not across projects yet

These remain errors for the node that holds them, raised only where a graph,
`cuenv ci` or `cuenv sync ci` reaches it:

- output references of another project (`content.tasks.build.stdout`, an
  image's `ref`);
- another project's task in a pipeline's `tasks` or a matrix entry's `task`,
  which fails only that pipeline;
- another project's task in a service's `watch.rebuild`, or in a service's or
  image's `dependsOn`;
- `outputFiles` on a group.

## Evaluation

The CUE bridge pins the fork at
[`806b303`](https://github.com/rawkode/cue/commit/806b30344b62), which shares
typed references into imported packages
([#619](https://github.com/cuenv/cuenv/pull/619)). cuenv evaluates chains of
`dependsOn` across imported projects in linear time: a chain of eight projects
plans in about a second. Plain `cue export` is slower. A project that depends
on an imported task with a dependency of its own takes a few seconds on CUE
v0.18, and longer chains take longer.

## Limitations

- A dependency on an imported task is told apart from a local one by the
  schema's stamp. On an older pinned schema without stamps, an imported task
  can bind a same-named task of the consumer: upgrade the schema before
  depending on imported tasks.
- A dependency on another project's sequence whose members are all nested
  sequences carries no stamp and is still bound by its bare name.
- The CUE bridge evaluates an imported project once per importer, and binding a
  reference builds each imported package once more to read its `name`.
  Importing a very large project only to read its files costs evaluation time
  in every command that evaluates the importer.

## cuetty

- The task list reads the `cuenvRef` stamp on a task group as part of the
  group, not as a task, and lists the tasks of projects on the new schema.
- Copying a selection clears it and confirms the copy with a toast.
